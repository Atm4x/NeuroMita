# ONNX-бэкенд RAG: устройство и сопровождение

Документ предназначен для разработчиков, меняющих экспорт моделей, runtime или установщик RAG. Пользовательская настройка описана в [руководстве RAG](../RAG_Guide.md), восстановление после ошибок — в [устранении неполадок](../TROUBLESHOOTING.md#конфликт-версий-зависимостей-rag).

## Выбор бэкенда и устройство запросов

`RAG_LOCAL_BACKEND=torch|onnx` выбирает реализацию только локальных эмбеддингов и реранкера; PyTorch остаётся значением по умолчанию. API-провайдеры эмбеддингов работают независимо. `RAG_ONNX_DEVICE=auto|dml|cpu` выбирает провайдер ONNX: `auto` предпочитает DirectML при его наличии, явный `dml` завершается ошибкой, если провайдер недоступен. Автоматического перехода на PyTorch нет.

Оба локальных бэкенда используют существующие RAG-запросы и общую приоритетную очередь. Правила планировщика не зависят от ONNX. Семантические настройки и ключ модели в базе не меняются.

## Установка и артефакты

Установщик использует управляемый ONNX runtime; на Windows — ONNX Runtime DirectML. Зависимость Torch для этого бэкенда выбирается как CPU Torch независимо от производителя GPU. Экспорт выполняется на CPU через Optimum в отдельном отменяемом subprocess. На запросах экспорт и скачивание не выполняются.

Исходный HF ID сохраняется. ONNX-копия лежит отдельно от исходных весов в `checkpoints/rag_onnx/<embeddings|reranker>/<hash>/`. Задачи экспорта:

| Модель | Задача Optimum |
| --- | --- |
| Эмбеддинги | `feature-extraction` |
| Обычный cross-encoder | `text-classification` |
| Qwen3-Reranker | `text-generation` без KV-кэша |

Готовность экспорта проверяется по манифесту и размерам всех файлов, включая внешние веса. Новый экспорт публикуется после подготовки. Ошибка экспорта сохраняет прежний артефакт; ошибка замены восстанавливает его. Повреждённый экспорт можно переустановить через AI Hub. Кастомная модель должна поддерживаться экспортёром Optimum; поддержка PyTorch этого не гарантирует.

## Выполнение и готовность

Сессии DirectML используют `ORT_SEQUENTIAL` и отключённый memory pattern. Вызовы одной сессии сериализованы. Для эмбеддингов на DirectML и для ONNX-реранкера используется батч 1. INT8 через bitsandbytes относится только к PyTorch.

Для архитектуры `qwen3` провайдер DirectML создаётся с `disable_metacommands=True` для обхода нативного падения в пути метакоманд ORT DirectML 1.24.4. Другие архитектуры сохраняют стандартные настройки метакоманд. Эта настройка сохраняет DirectML; она не отключает оптимизации графа и не выбирает CPU.

При загрузке выполняется пробное вычисление. Сообщение `[RAG][ONNX] Loaded` и успешный прогрев появляются после получения непустого конечного результата. Это не перехватывает произвольные нативные падения и не заменяет проверку целевых входов. Наличие DirectML в сессии не доказывает, что каждый оператор исполняется на GPU: неподдерживаемые операции могут передаваться CPU.

Эмбеддинги используют CLS или last-token pooling по архитектуре и L2-нормализацию. Qwen3-Reranker использует вероятности токенов `yes`/`no`, как PyTorch-путь.

## Конфликты окружений и таймауты

При несовместимой установленной версии зависимости `ensure_runtime_ready()` выдаёт `RAG dependency version conflict` с версией, требованием и рекомендацией split. Отсутствующий пакет сохраняет ошибку `RAG backend is not installed`. Контроллер сохраняет диагностику активации и прекращает автоматические повторы прогрева эмбеддингов при конфликте версий; события установки, смены настроек и успешного перезапуска позволяют начать прогрев снова.

`RAG_EMBED_TIMEOUT_SEC` по умолчанию равен 60 секундам. `RAG_RERANK_TIMEOUT_SEC=0` означает расчёт по числу кандидатов; явные положительные значения ограничены диапазоном 1–3600 секунд. Изменения применяются к следующим запросам. Время включает очередь; фоновые пакеты эмбеддингов могут получать больший бюджет. Прогрев и установка имеют отдельные бюджеты.

Один бюджет передаётся worker-запросу и ожиданию результата, включая запасной локальный обработчик. Значения выше 300 секунд не должны обрезаться стандартным дедлайном worker-запроса.

## Проверка изменений

Основные проверки находятся в `src/utils/Testing/test_rag_onnx.py`, `test_rag_request_timeouts.py`, `test_rag_runtime_context.py`, `test_rag_restart_state.py` и `test_runtime_environments.py`. Они покрывают выбор зависимостей, параметры сессии, pooling и оценки, пробное вычисление, артефакты и восстановление, таймауты и диагностику конфликтов.

При изменении runtime или экспорта отдельно проверяйте реальные веса: CPU и DirectML, эмбеддинги и реранкер, короткие и обрезанные до 512 токенов входы, повторные запросы и сравнение с PyTorch. Профиль ONNX Runtime помогает подтвердить провайдера отдельных операций. Ускорение, потребление VRAM и поведение целевой видеокарты требуют отдельных измерений. Результаты конкретных прогонов сохраняйте в отчёте проверки или описании PR.
