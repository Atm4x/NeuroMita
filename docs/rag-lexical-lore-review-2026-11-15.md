## Что реально получила модель

- В контрольном запросе о первой встрече без имён реальный сборщик выдаёт обоим персонажам раннюю погоню первой среди лорных записей и отделяет неизвестную первую встречу от известного эпизода. Добрая ссылается на свидетельства, Безумная помнит собственный опыт.
- В вопросах о записи людей у Безумной доступны записи из её опыта, у Доброй — знания из расследования, у Коротковолосой — пересказ чужих слов. На чистой базе и старом снимке ни у Кепочки, ни у Милы, Жуткой, Призрачной и Сонной в контрольных RAG-блоках не найдено текста заводских сидов с процедурой. Из статических материалов убраны конфликтующие блоки и сценарий, где Добрая окончательно побеждает Безумную и восстанавливает память Кепочке.
- Отображение давности идёт от единого якоря мира: сид показывает приблизительное время события либо «время события неизвестно». Повторная загрузка восьми персонажей на снимке оставила якорь и 1 133 видимых лорных сида стабильными, без дублей; замена старых сидов и загрузка не изменили ни одного существовавшего активного пользовательского факта. Старый заводской остров отношений Доброй обновляется на месте только при точном совпадении; пользовательские договорённости сохраняются.
- Совмещённый режим всё ещё иногда подмешивает нерелевантные результаты: четыре из шести отрицательных формулировок дают непустую выдачу. Из десяти промахов на старом снимке — разговорные варианты о доме Жуткой, прежнем игроке и выходе между версиями. Непустая выдача на отрицательном запросе сама по себе не означает, что персонаж получил закрытые сведения.

## Проверка сцен и авторское ревью

- **Первая встреча.** В записи Добрая отвечала о знакомстве с игроком. Теперь в промпте отдельно указано, что вопрос, обращённый к обеим Митам, относится к их знакомству друг с другом. Для ручного прогона: обе Миты называют погоню, если уместно, но не придумывают первое знакомство и не повторяют ответ друг друга.
- **Перемирие.** В записи Безумная согласилась при условии снятия эффектов, а Добрая позже отвергла перемирие, не разобрав условия. Проверить три варианта генерации: Безумная после выполненного условия сохраняет характер и соблюдает уговор; Добрая до рассказа о договоре не осведомлена; после рассказа оценивает условия и может отказать по конкретной причине. Проверен входной контекст и политика памяти; повторные ответы игровой модели не снимались.
- **Повторные реплики: исходное наблюдение.** В двух сохранённых запросах одной сцены повторились 3 из 7 и 7 из 12 строк с тегом DIALOGUE. Проследить одной реплике путь через входное событие и сохранённую историю; подавлять повтор по идентификатору события, сохраняя намеренные повторы и реплики разных персонажей.
- **Отдельная задача: внешность.** Запрос Безумной передавал признаки формы и причёски, а ответ ушёл от вопроса о цвете волос. Сначала сравнить авторитетное состояние на стороне Unity и его представление в Python: имя формы, причёска, известный цвет и эффект освещения. При отсутствии данных передавать это явно. Unity здесь не менялась.
- **Нужно решение автора:** точные обстоятельства первой встречи Доброй и Безумной; маршрут Доброй от Ядра и история кольца; дальнейшая судьба первого игрока Безумной. Эти детали не утверждались.

Команда: из корня проекта запустить src/utils/Testing/rag_tester/canon_benchmark.py с параметрами --db scratch.db --output metrics.json. Для существующего мира использовать отдельный SQLite-снимок и --existing. Исходная пользовательская база не изменялась. Ни базы, ни записи диалогов, ни частные UUID в PR не входят.

## Офлайн-аудит и запись памяти

По двум локальным JSONL всего 2 631 запись. В ноябре из 1 403 запросов с ID персонажа текущий Python-парсер разобрал 1 385 ответов; 801 запрос без ID учитывается отдельно. Найдены 411 команд добавления и 3 обновления памяти. У 906 из 1 085 ноябрьских запросов с распознанными блоками доставленного диалога повторился хотя бы один полный текст такого блока; повтор заголовка состава сцены считался отдельно. Совпадение текста не доказывает совпадение идентификатора события.

Заводской канон теперь только для чтения в обычных командах памяти. Тест проигрывает JSON с обновлением, удалением и смешанным объединением на временной SQLite: сид и факт остаются целыми. Обычное обновление факта и точечный вывод заводского сида через миграцию продолжают работать.

Аудит загружает журнал как входные данные для проверки формата, а не как снимок мира до конкретного запроса. Следующий шаг — воспроизводить события сцены по идентификаторам через сборщик контекста, затем проверять запись новой памяти с сохранением источника. Это позволит проверять контракт без вызова модели и без повторного применения старых команд к живому миру.

Прогон обычных `memory_add`: `python src/utils/Testing/generation_tester/finetune_memory_replay.py <samples.jsonl> --snapshot <snapshot.db>`. Утилита открывает исходный снимок только для чтения, проигрывает предложения через рабочий парсер и код записи на временной копии, выводит только счётчики. Используется время из выгрузки. Обновления, удаления, объединения, острова и вытеснение по лимиту исключены из эксперимента: снимок не соответствует состоянию до каждого ответа.

До правки токены короче трёх символов не учитывались: «принёс ключ в 5 часов», «не принёс ключ в 5 часов» и «принёс ключ в 6 часов» могли заменить друг друга. Теперь при добавлении и фоновом обслуживании автоматически считаются копиями только обычные факты одного персонажа с совпадающими текстом, временем записи и сущностями. Исходный текст и дата сохраняются, повышается только приоритет. Повтор слов в другом эпизоде сохраняется. Повторная загрузка стартового факта не возрождает убранный канон с тем же текстом. Лимит памяти в игре продолжает действовать. Эти цифры показывают эффект алгоритма на одной копии, а не количество реальных исторических перезаписей; редактирование источника явной командой и ручная векторная очистка остаются отдельными путями.

## Повторная доставка DialogueAuto

Аудит ноября нашёл 614 запросов, в которых один и тот же текст одновременно присутствовал в [Current UnityEvent] и [DialogueAuto]. Причина в сборке запроса, до адаптера Gemini: вложенный контекст генерации терял ID событий, уже переданных во входе реакции. Наследуем эти ID и показываем целевой факт отдельно только тогда, когда он ещё не передан. Офлайн-тест проходит через вход Unity, SQLite-хронологию, сборщик истории и промпта, а затем проверяет сериализацию Gemini: один текст в роли user с маркером [RUNTIME EVENT], отправки в API нет.

В истории известные старые обёртки DialogueAuto проецируются как речь с автором. Состав сцены и инструкции ответить сохраняются только во входе текущего хода. Исходные записи в SQLite сохранены. Офлайн-прогон той же функции по архиву распознал 6 854 исторические обёртки в ноябре; суммарная разница — около 4,98 млн символов по снимкам запросов. Это оценка объёма повторно показанных обёрток, а не замер токенов нового приложения. Старые сводки, построенные с предыдущей проекцией, не используются как актуальный кэш.

Включение текущего события и его сохранение теперь учитывают один и тот же явный список наблюдателей. Пакет приватных реакций без доступных получателю событий не возвращает исходный скрытый повод через запасной путь. Повтор отправки с тем же идентификатором запроса сохраняет один набор событий; одинаковая фраза в двух отдельных доставках остаётся возможной. У старых Unity-строк нет отдельного ID исходной реплики между запросами, поэтому по совпадению текста их не удаляем.

## Источник сведений при сжатии

Отдельно распознаны 24 октябрьских и 801 ноябрьский запрос суммаризации без ID персонажа. В их входных историях соответственно 1 101 и 20 865 строк подписаны обобщённо «Character or System», а 459 и 3 384 — «Player». Числа включают одни и те же строки в последовательных запросах; без метаданных исходных сообщений нельзя установить, сколько строк «Player» в действительности принадлежали другим персонажам. 19 и 800 запросов содержат технические метки времени.

Подтверждённая причина в Python: сборщик сжатия определял автора только по роли. Но в персональной хронологии роль user используется и для других персонажей, и для наблюдений мира. Теперь общий форматтер сохраняет speaker/sender, различает наблюдение, событие, системную заметку и прежнюю сводку. Он используется в суммаризации, локальном запасном варианте и необязательном извлечении фактов. Техническое время строки в текст сжатия не переносится; порядок и время, явно сказанное в диалоге, остаются. Подстановка переменных шаблона делается за один проход, чтобы слова вида {previous_summary} внутри реплики не заменялись содержимым сводки. Старые кэши персональной хронологии отвергаются версией digest v3, исходные события сохраняются.

Офлайн-проверка проходит через настоящую персональную хронологию: приватная договорённость Безумной не входит в историю Доброй; рассказ Милы про логи остаётся подписан Милой в запросе сжатия и локальном запасном варианте. Промпт извлечения фактов требует сохранить источник в самом тексте, а общий промпт памяти — сохранять источники при обновлении/объединении и разделять конфликтующие сообщения. Сводка в итоговом контексте отмечена как производная запись о прошлом.

**Граница гарантии:** атрибуцию входа и видимость проверяет код; правдивость свободно сформулированной моделью сводки или memory_update он семантически не проверяет. Старая пользовательская сводка и живые факты не переписываются автоматически. Без новой схемы источников и проверки результата нельзя обещать, что произвольный ответ модели никогда не превратит пересказ в личный опыт. В этом цикле проверены данные и инструкции, отправляемые модели; новые ответы не генерировались.

## Повторная диагностика промахов

У benchmark есть параметр --diagnostics для локального JSON: номер случая, источник и оценка каждого результата, число целевых записей и их ранги в широком поиске без порога (до 100). Текст выдачи и ID не экспортируются. При подсчёте целевым считается только источник memory: совпавший числовой ID истории не может дать ложное попадание. Это выдача поиска до фильтрации и сборки итогового запроса, а не подтверждение доставки модели.

На свежей копии снимка и чистой базе совмещённый Recall@5 повторился: 0,778 и 0,870. На снимке из десяти формулировок без попадания в топ-5 девять находят цель при широком поиске: ранги 6–100; вопрос «Можешь просто захотеть и выйти из дома?» цели не находит. Для него настройка весов не поможет. На чистой базе цель этого же вопроса не найдена, остальные четыре промаха находятся на рангах 6, 10, 16 и 26. Пустота на отрицательном вопросе оценивается отдельно: непустая выдача не доказывает ни релевантность, ни утечку закрытого знания. Глобальные веса и порог не менялись.

## Лексика, Qwen и граф на одних вопросах

44 вопроса по две формулировки (30 исходных + 14 по новым сидам и границам), включая 10 отрицательных формулировок. Сравниваются стартовые и живые воспоминания, при включении графа — также данные графа; поиск по истории и хвост диалога выключены, чтобы изолировать вклад профиля. Целями метрик служат записи памяти, графовые связи считаются отдельно. Лимит 5, порог 0,4. Qwen3-Embedding-0.6B ONNX на CPU, без запроса генерации. Издержки индексации не включены в задержку запроса; p50/p95 ниже ориентировочные, часть прогонов выполнялась параллельно.

| Профиль | Чистая R@5 / MRR@5 | Снимок R@5 / MRR@5 | Снимок p50/p95, мс |
| --- | ---: | ---: | ---: |
| Ключевые слова + FTS | 0,801 / 0,663 | 0,769 / 0,629 | 125 / 262 |
| Только Qwen | 0,795 / 0,673 | 0,462 / 0,377 | 350 / 611 |
| Qwen + лексика | 0,814 / 0,700 | 0,731 / 0,595 | 465 / 939 |
| Лексика + граф | 0,801 / 0,663 | 0,769 / 0,627 | 92 / 213 |
| Qwen + лексика + граф | 0,827 / 0,703 | 0,731 / 0,605 | 334 / 405 |

До исправления линейный ранжировщик отбрасывал оценку совпадения графовой связи. Исправление учитывает совпадение и уверенность связи; защищённые стартовые связи не получают прибавку за дату импорта. Имена в графе сопоставляются по нормализованным словам и известным RU/EN-алиасам. На чистой базе в лексическом профиле с графом графовая связь попала в топ-5 для 12 из 88 формулировок против двух до исправления, Recall@5 по целевым воспоминаниям не снизился. В старом мире граф не улучшил Recall@5; автоматического повышения его веса в этом эксперименте не применяли.

Воспроизведение: `python src/utils/Testing/rag_tester/profile_benchmark.py --output report.json`, для копии старого мира добавить `--snapshot snapshot.db`. Нужны установленное окружение приложения с ONNX и transformers и локальный экспорт Qwen в `NEUROMITA_CHECKPOINTS_DIR`. Профили и расширенные метрики сохраняются в JSON, тексты реальных результатов в него не входят. Предупреждение токенизатора о Mistral regex не использовалось как основание менять конфигурацию Qwen; в этом замере сохранён текущий токенизатор приложения.

## Игровой хвост и смена темы

Взяты три ноябрьских запроса: вопрос Доброй о первой встрече, перемирие с Безумной и вопрос Доброй об условиях чужого перемирия. На временной копии мира для каждой сцены активируются только две вручную выбранные строки диалога из сохранённого запроса. Исходный последний вопрос заменяется контрольной формулировкой; ответы, служебные блоки запроса и приватные UUID не экспортируются. Проверка ищет ожидаемые и закрытые признаки только в RAG-сообщении, реально добавленном сборщиком промпта.

| Контроль | До, хвост 0 / 1 / 2 | После, хвост 0 / 1 / 2 |
| --- | --- | --- |
| Ранняя погоня у Доброй: прямой и короткий вопросы | есть / есть / есть | есть / есть / есть |
| Переход от перемирия к вопросу о сбросе мира | есть / нет / нет | есть / есть / есть |
| Условия частного перемирия в контексте Доброй | нет / нет / нет | нет / нет / нет |

В случае смены темы прошлые слова заполняли список ключевых слов и вытесняли нужную запись. Теперь ключевые слова хвоста дополняют только вопросы короче трёх значимых слов; формирование векторного запроса не изменилось. Это условие проверяет отдельный тест. Прогон не измеряет поведение модели и не доказывает отсутствие утечек по всем возможным формулировкам.

Команда: `python src/utils/Testing/rag_tester/scene_query_replay.py <samples.jsonl> <local-manifest.json> --snapshot <snapshot.db> --output <report.json>`. Манифест — массив объектов с ключами `label`, `sample` (UUID из локальной выгрузки), `character`, `tail` (список объектов с `index` начиная с нуля и `speaker`) и `questions` (для каждого вопроса `label`, `text`, необязательные `expected` и `forbidden`: словари меток со списками фраз). В отчёте сохраняются метки и булевы результаты, а не реплики.

## Подбор весов и проверка переноса

Порог 0,4 и лимит 5 оставлены прежними. На исходных 30 вопросах проверены базовые ключевые слова + FTS + граф, повышение веса ключевых слов с 0,6 до 0,8 и повышение веса FTS с 0,3 до 0,5. Последний профиль называется `lexical_fts`; вес FTS также масштабирует доказательность графовой связи. 14 новых вопросов не участвовали в выборе и были прогнаны отдельно.

| Набор | Базовый R@5 / MRR@5 | Больше веса FTS R@5 / MRR@5 |
| --- | ---: | ---: |
| Исходные, чистая база | 0,870 / 0,744 | 0,870 / 0,757 |
| Исходные, старый снимок | 0,806 / 0,683 | 0,843 / 0,718 |
| Отложенные, чистая база | 0,875 / 0,614 | 0,875 / 0,644 |
| Отложенные, старый снимок | 0,708 / 0,544 | 0,750 / 0,569 |

Более высокий вес только ключевых слов улучшил MRR на исходном снимке до 0,694, сохранив Recall@5. Снижение веса Qwen до 0,35 с одновременным повышением веса лексики на исходных вопросах снимка не улучшило Recall@5 (0,722 у обоих гибридных профилей). Число непустых выдач на отрицательных формулировках при выборе `lexical_fts` не изменилось; непустой результат не означает, что он отвечает на вопрос.

На трёх архивных сценах старого мира `lexical_fts` и базовый графовый профиль сохранили раннюю погоню (6/6 вариантов) и запись о сбросе (3/3); маркеров закрытых условий перемирия у Доброй не обнаружено (0/3 у каждого). Это проверка фактически собранных RAG-сообщений.

Отдельно исправлен пропуск на этапе поиска. Для «Можешь просто захотеть и выйти из дома?» настройка веса не находила целевой сид даже в широкой выдаче. Формулировка существующего правила теперь явно связывает выход из дома с переходом между версиями; прежний текст выводится точечной миграцией. Обе формулировки о переходе попали в топ-5 на обеих базах. На исходных вопросах снимка R@5 вырос с 0,806 до 0,843 на базовом профиле и с 0,843 до 0,880 на `lexical_fts`; на чистой базе с 0,870 до 0,907 у обоих. Это отдельный эффект исправления словаря.

Команды: `profile_benchmark.py --cases original --profiles lexical_graph lexical_keyword lexical_fts` для подбора, `--cases new --profiles lexical_graph lexical_fts` для отложенного набора, `scene_query_replay.py --profiles lexical_graph lexical_fts` для архивных сцен. К параметрам добавить обычные пути к входам и отчёту. Лексические варианты не загружают модель; для повторных векторных замеров можно добавить `--cache-queries`, но задержки такого прогона несопоставимы. В игру профиль автоматически не включается.

## Архивные реплики в общем поиске

Архивный индекс может хранить устаревший текст или ссылаться на событие, которое персонажу ещё не видно. Раньше сборщик промпта отбрасывал такие результаты после выбора top-5, а команда поиска памяти возвращала их напрямую. Теперь общее ядро сверяет кандидатов из истории с веткой, персонажем и границей текущего хода до объединения выдач и реранкера. Текст, говорящий и адресаты берутся из журнала. Регрессионная проверка оставляет доступную реплику в топ-1 при наличии более сильного закрытого совпадения и реплики из будущего хода. Внутренние лимиты самих источников кандидатов остаются прежними.

На старом снимке с действующим журналом проверены те же 88 формулировок. Разметка в этой таблице оценивает целевые сиды: полезность найденных старых реплик по ней не измеряется.

| Профиль / архив | R@3 | R@5 | MRR@5 | nDCG@5 | P@5 | Запросов с архивом в top-5 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Базовый / выключен | 0,724 | 0,801 | 0,653 | 0,676 | 0,172 | 0 |
| Базовый / включён | 0,724 | 0,801 | 0,647 | 0,672 | 0,172 | 10 |
| `lexical_fts` / выключен | 0,750 | 0,840 | 0,698 | 0,720 | 0,179 | 0 |
| `lexical_fts` / включён | 0,750 | 0,827 | 0,689 | 0,711 | 0,177 | 18 |

У всех вариантов две пустые выдачи. Один дополнительный промах `lexical_fts`: в вопросе о близости Доброй и Кепочки старая реплика занимает третью позицию, целевой сид сдвигается с пятой на шестую. Другая формулировка того же вопроса проходит. Это пример для настройки конкуренции источников после разметки вопросов, для которых нужна именно история. Задержки параллельных прогонов и заполнение кеша журнала не позволяют оценить чистую цену поиска по истории; у `lexical_fts` наблюдалось 74/212 мс без архива и 70/149 мс с архивом (p50/p95).

Воспроизведение: `profile_benchmark.py --profiles lexical_graph lexical_fts --snapshot snapshot.db --output report.json --search-history`. Для контрольного прогона убрать `--search-history` и выбрать другой путь отчёта. Этот флаг требует существующий журнал; векторный архив в этом сравнении не индексировался.

## Вопросы, на которые отвечает живая история

В отдельном локальном корпусе девять архивных эпизодов Доброй, Сонной и Кепочки и три контроля у персонажей, которые не присутствовали. Для каждого случая написаны две новые формулировки. Цель — точная реплика с заданным ID, предварительно сверенная с журналом видимости. Удалённые реплики и строки, отсутствующие в журнале, не считаются целями. Слова игрока и старые ответы персонажей не превращаются в канон.

Локальный манифест — массив объектов с полями `label`, `character` (кого спрашиваем), `source_character` (кому принадлежит строка архива), `message_id`, `visible` (булево) и `questions` (ровно две формулировки). Команда: `profile_benchmark.py --profiles lexical_graph lexical_fts --snapshot snapshot.db --output report.json --search-history --history-cases archive-cases.json`. Для прогона только живых вопросов добавить `--history-only`. В отчёт идут только метки, ранги, типы источников и наличие целевого текста в собранном RAG-сообщении. Тексты, идентификаторы и снимок остаются локально.

Исходный `lexical_fts` доставил в промпт точную реплику в 14 из 18 доступных формулировок, базовый — в 12 из 18. Закрытый текст не пришёл в промпт ни в одном из 6 контролей. У `lexical_fts` три промаха нашлись в широкой выдаче на местах 6, 24 и 41; один разговорный перефраз не нашёл точную реплику даже при широком лимите. Эти метрики оценивают одну размеченную реплику на вопрос; другие относящиеся к эпизоду записи тоже могут быть полезны.

Отдельный синтетический тест показал, что исключённые реплики всё ещё влияли на шкалу FTS: более сильное совпадение закрытой реплики обнуляло FTS-балл единственной доступной. Нормализация архивных баллов теперь выполняется после проверки видимости. Она по-прежнему нормализует результаты отдельно от сидов и не меняет глобальные веса. Повторный прогон сохранил 14/18 доставленных архивных реплик и 0/6 закрытых у `lexical_fts`; R@5 на 88 канонических формулировках остался 0,827. Четыре оставшихся промаха позволяют отдельно проверить небольшой сдвиг ранга и смысловые перефразы.

На отложенном наборе из семи других архивных эпизодов `lexical_fts` доставил 12 из 14 доступных реплик (MRR@5 0,592), базовый профиль — 9 из 14 (MRR@5 0,518). Ни один из четырёх закрытых контролей не попал в RAG-сообщение. Этот набор не использовался при подборе весов; манифест также остаётся локально.

Активный хвост запроса теперь проверяется по тому же журналу: SQLite определяет, какие строки активны, а журнал подтверждает доступность к началу хода и возвращает их текст и говорящего. Это применяется к ключевым словам, обоим режимам векторной сборки запроса и данным участников для ранжирования. При отсеивании новые неподходящие строки не занимают места в хвосте: поиск продолжает чтение до доступной реплики. В тестовой фикстуре поздняя и закрытая строки не меняют запрос, а устаревший текст доступной строки заменяется текстом журнала. Изолированный тестер без журнала по-прежнему принимает явно загруженные сценарии.

Для сравнения с Qwen тот же запуск принимает `--profiles lexical_fts vector hybrid_graph hybrid_lexical`. На временной копии тестер переиспользует векторы того же эмбеддера и досчитывает отсутствующие только для архивных строк, видимость которых подтверждена журналом. `--cache-queries` сравнивает качество с общим кешем векторов запросов; такие задержки нельзя считать производительностью отдельных профилей.

## Qwen с включённым архивом

В одном запуске на Python 3.12 приложения сравнили 88 канонических формулировок и 24 архивные, включая шесть закрытых контролей. В снимке уже существовали векторы Qwen для всех 590 доступных архивных строк выбранных персонажей; генерация не вызывалась. В текстах используются разные источники разметки: ожидаемый канонический сид и точная реплика живой истории.

| Профиль | Канон R@5 / MRR@5 | Архив top-3 / передан в промпт | Архив MRR@5 | Закрытый архив в промпте |
| --- | ---: | ---: | ---: | ---: |
| `lexical_fts` | 0,808 / 0,674 | 10 / 12 из 18 | 0,435 | 0 из 6 |
| Qwen | 0,474 / 0,390 | 11 / 13 из 18 | 0,479 | 0 из 6 |
| Qwen + лексика + граф | 0,744 / 0,612 | 13 / 14 из 18 | 0,576 | 0 из 6 |
| Qwen + лексика + граф, больше веса лексике | 0,744 / 0,608 | 11 / 12 из 18 | 0,382 | 0 из 6 |

Вектор поднял два трудных перефраза о свечении глаз и цветах одежды; смешанный поиск лучше балансировал их с точными формулировками, но хуже лексики находил канон. Один перефраз о дистанции не нашёл точную реплику ни в одном профиле. Целиком заменять лексический поиск векторным по этому тесту оснований нет.

Отдельный лексический прогон после фикса хвоста в рабочем Python 3.11 подтвердил прежние 0,827 по канону и 14/18 по архиву. Этот Python использует встроенный стеммер; в Python 3.12 приложения доступен `pymorphy3`. Контроль без векторов в Python 3.12 воспроизвёл 0,808 и 12/18. В этом же окружении, с отключением только `pymorphy3` в диагностическом процессе, встроенный стеммер вернул те же 0,827 и 14/18, что и Python 3.11. Глобальный режим нормализации не изменён: для решения о нём нужен отложенный набор. JSON теперь сохраняет версии Python и SQLite и доступный способ нормализации русского языка.

На исходном архивном наборе в Python 3.11 снижение общего веса совпадения сущностей с 0,5 до 0,2 оставило R@5 канона 0,827 и снизило доставку архива до 13/18. При нулевом весе канон вырос до 0,840, но архив также остался на 13/18. Этот вес влияет и на граф, поэтому по двум метрикам его не меняем.
