# Сбор, оценивание, хранение и экспорт данных диалога для дообучения

> Состояние проверки: статически подтверждённые кодом сценарии Python Core + GUI, без запуска PyQt6. Это самостоятельная пользовательская функция NeuroMita, **не** обучение/инференс модели и не требование переносить AI inference на Rust. Source root: Python `src` из CodeNow.zip.

## CAP-DATA-FINETUNE — сбор обучающих примеров

**Статус:** `CONDITIONAL` — настройка включения сбора и завершённый запрос/ответ. **Источники:** `src/managers/finetune_collector.py:25-125`, `src/ui/settings/data_settings.py:89-128`, `src/controllers/gui/finetune_data_view_model.py:18-65`.

Пользователь включает/выключает запись пар запрос/ответ. При сохранении образца создаётся UUID и UTC timestamp, сохраняются идентификатор/имя персонажа, идентификатор модели и провайдера, `protocol_id`/`dialect_id`, параметры семплирования, флаг подключения игры, массив `messages`, результат `response`, рейтинг (первоначально `null`) и фактический `usage` при наличии. Это **снимок одного генерационного взаимодействия**, а не сама история сообщений. Записи append-only в обычном случае хранятся в `FineTuneData/samples_YYYYMM.jsonl`, отделённо от SQLite истории. Действующие значения по умолчанию: сбор включён; максимум 50 примеров, если `FINETUNE_UNLIMITED` выключен. Глобальная настройка базы может определяться `NEUROMITA_BASE_DIR`/текущим рабочим каталогом; возможность поменять папку вынесена в UI.

Сбор предоставляет `sample_id` и переменную «последний незабранный ID образца» для последующей пользовательской оценки. В UI отдельная настройка `SHOW_MESSAGE_RATING_CONTROLS` включает кнопки положительной/отрицательной оценки у ответа ассистента **при активном сборе данных** (`data_settings.py:111-128`). `update_rating(sample_id, ±1)` находит запись по UUID и перезаписывает JSONL-строку с `rating`, не изменяя текст ответа (`finetune_collector.py:169-209`). Рейтинги — метаданные к сэмплу и могут фильтроваться при экспорте.

## CAP-DATA-FINETUNE-RETENTION — лимит, статистика, удаление, папка

**Статус:** `ACTIVE` для UI управления, эффект зависит от состояния сборщика. **Источники:** `src/managers/finetune_collector.py:47-61,127-165,213-275,397-420`, `src/ui/settings/data_settings.py:130-277,282-420`, `src/controllers/gui/finetune_data_view_model.py:45-148`.

Пользователь задаёт максимум сохранённых последних записей (1–1 000 000 в UI) либо снимает лимит. При включённом лимите старые строки удаляются **по месячным файлам от ранних к поздним**; пустые файлы удаляются. Параметры настраиваются независимо от отображения рейтингов. Пользователь может выбрать каталог, обновить статистику, принудительно применить лимит и очистить все `samples_*.jsonl` с подтверждением. Статистика содержит всего записей, с рейтингом, положительных/отрицательных, распределение по персонажам и моделям; повторная выдача может использовать кэш на сигнатуре файлов (`mtime`, размер). GUI отображает `loading`, `error`, доступность коллектора и обновление ревизии, а длительные действия выполняет через `run_exclusive` или `run_coalesced`.

Жизненный цикл: изменение настройки → сохранение настройки → асинхронное применение лимита/обновление статистики → отображение результата; очистка — отдельное подтверждённое действие и не тождественна удалению SQLite-истории.

## CAP-DATA-FINETUNE-EXPORT — выборка и два формата выгрузки

**Статус:** `ACTIVE` через settings/ExportDialog. **Источники:** `src/ui/dialogs/export_dialog.py:23-260`, `src/controllers/gui/finetune_data_view_model.py:23-44`, `src/managers/finetune_collector.py:279-420`.

Пользователь открывает диалог экспорта и задаёт период включительно (временные отметки приводятся к UTC), подмножество персонажей (ничего не выбрано — все), фильтр рейтинга (все; исключить отрицательные, оставив положительные и без оценки; только положительные) и формат. UI пересчитывает число подходящих записей до экспорта. Сборщик умеет также фильтровать по списку моделей, хотя текущий диалог не предоставляет отдельный model picker: не выдавать API-возможность за действующий UI-элемент.

**Raw JSONL** сохраняет самодостаточные записи с полными метаданными. **ShareGPT / ChatML** строит `conversations`: `system → system`, `user → human`, `assistant → gpt`, итоговый ответ добавляет последним сообщением `gpt`. Мультимодальный список в контексте уплощается до доступных текстовых частей. Поэтому ShareGPT — **потеря структурной/мультимодальной части исходных данных по определению конвертации**; для полной диагностики нужен Raw JSONL. Экспорт принимает выбранный пользователем путь, информирует о числе записей, ошибки показываются в GUI. Не обнаружено автоматического обучения/отправки файла по сети из данного диалога.

## CAP-DATA-GENERATION-INGRESS — опциональная запись входа до промпта

**Статус:** `CONDITIONAL`, отдельный debug toggle, по умолчанию отключён. **Источник:** `src/managers/generation_input_collector.py:15-60`.

`GenerationInputCollector` пишет `SavedMessages/last_generation_input.json` и помесячный `generation_inputs_YYYYMM.jsonl` (UUID + timestamp + входной payload). Назначение — диагностика и воспроизведение исходного ingress до конструирования промпта. **Не смешивать**: FineTune snapshot — итоговый запрос к LLM с ответом и usage, а generation ingress — данные до преобразования в отправляемый запрос. Обязательность этой функции для будущей версии зависит от подтверждения действующих вызовов сборщика; один класс без проверенного вызова не доказывает использование конкретного payload. Реальная точка вызова подлежит отдельной трассировке.

## Граница функциональности и неясности

- В `data_settings.py:71-84` присутствует **внешняя ссылка** на папку сбора данных. Это внешняя точка выгрузки, не автоматическая синхронизация Core с Google Drive.
- Настройки `FINETUNE_COLLECTION_ENABLED`, `FINETUNE_UNLIMITED`, `FINETUNE_MAX_RECORDS`, `SHOW_MESSAGE_RATING_CONTROLS`, `DEBUG_CAPTURE_GENERATION_INPUT_ENABLED` принадлежат разным целям: сбор, удержание, кнопки оценки, debugging.
- Нужна трассировка: какие генерационные маршруты вызывают `save_sample`, когда и как рейтинг связанного chat bubble привязан к UUID, каковы правила обработки отменённых/неуспешных ответов.
- Rust архитектура **пока не выбирается**; нужно сохранить семантические возможности `RecordSample`, `RateSample`, `GetStats`, `ApplyRetention`, `QuerySamples`, `ExportRaw`, `ExportShareGPT`, `ClearSamples` и диагностического `RecordIngress`.

## Требования и проверка паритета

`REQ-DATA-FT-01`: сохранять полные контексты успешных запросов и ответов с идентичностью персонажа/модели и необязательным provider usage при включённом сборе. `REQ-DATA-FT-02`: назначать/обновлять пользовательскую оценку на конкретный sample UUID. `REQ-DATA-FT-03`: поддерживать ограниченное/неограниченное накопление, управление папкой и сбор статистики. `REQ-DATA-FT-04`: выгружать фильтрованные сэмплы в Raw JSONL и ShareGPT, явно различая степень сохранения исходных данных. `REQ-DATA-FT-05`: обособить диагностические ingress captures от обучающих пар запроса/ответа.
