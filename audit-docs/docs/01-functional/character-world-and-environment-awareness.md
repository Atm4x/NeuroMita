# Контекст игрового мира и осведомлённость персонажа о приложении

**Назначение.** Восстановить две самостоятельные функции, которые на каждом ходе снабжают LLM актуальными сведениями о мире и доступных пользователю возможностях. Эти сведения не являются долговременной памятью персонажа, объектной моделью Unity или настройками целевого Rust GUI. Статус: **ACTIVE**, основные production call paths подтверждены статическим просмотром.

## CAP-WORLD-001 — смысл локации для конкретного персонажа

**Источники:** `src/domain/world_character_relations.py:10-74,77-220,223-242`; `src/domain/world_contexts/{crazy,kind,cappie,mila,sleepy,creepy,ghost}_house.json`; `src/controllers/model_controller.py:1409-1429`; `src/controllers/prompt_controller.py:891-908,1026-1067,1180-1183`.

**Пользовательский смысл:** один и тот же дом трактуется разными персонажами по-разному — свой дом, прежний дом, гостевой дом или индивидуальный контекст из данных мира. Это влияет на то, что персонаж *знает/считает о месте*, а не на физический перенос персонажа, права доступа или навигацию Unity.

**Данные:** `worldMita`, затем `worldPlayer`, иначе пустой world ID; отвечающий `character_id`; предустановленные JSON-описания с `world_id`, `display_name`, `owner`, `former_owners`, `default_context`, `character_contexts`, `character_relations`. Поставлены семь ресурсов домов (`CrazyHouse`, `KindHouse`, `CappieHouse`, `MilaHouse`, `SleepyHouse`, `CreepyHouse`, `GhostHouse`). Факты о конкретной принадлежности остальных персонажей определяются самими JSON; не следует достраивать их из имён.

**Алгоритм разрешения:**

1. World ID и известные Character ID приводятся к устойчивым написаниям. Для известных домов есть явные псевдонимы; для кастомных ID допускается сопоставление без неалфавитно-цифровых разделителей.
2. Если описание мира не найдено, текст для промпта пуст; структурированная версия возвращает `relation=visitor`, `facts=[]`.
3. При наличии персонального `character_contexts[character]` берётся именно оно. Тип отношения — явно заданный, иначе `home`/`former_home`/`custom`.
4. В отсутствие персонального текста владелец получает `home`, бывший владелец — `former_home`, остальные — `visitor` и `default_context`.
5. `ModelController` обогащает **частную копию** snapshot мира (`game_state["character_world_context"]`), затем `PromptController` заключает результат в `[Character World Context]` как временный system-context.

**Состояние и границы.** JSON lore — статический resource catalogue; принадлежность и world ID — данные сессии Unity; ответ выбран для конкретного `character_id` и не должен мутировать общий `GameState`. В текущей сборке файлы грузятся через `importlib.resources`, что допускает как обычный source, так и архивный `NeuroMita.pyz`. Индивидуальные contexts не формируют новые долговременные memories. Пустой неизвестный мир не вызывает автосоздания дома.

**Инварианты для будущего parity:** персонажи с разной идентичностью могут одновременно получать разные толкования того же мира; псевдонимы не должны менять canonical ID; отсутствие знания отличается от знания «гость»; world lore и игровой state имеют разную provenance и lifetime; исходный snapshot одного запроса не становится глобальным prompt-текстом другого.

## CAP-ENV-001 — текущая осведомлённость о возможностях NeuroMita

**Источники:** `src/services/contracts.py:88-111,577-600`; `src/services/character_environment_context.py:22-207,210-304`; `src/controllers/main_controller.py:150-162`; `src/controllers/prompt_controller.py:243-284,1204-1212`; `src/controllers/gui/presentation_hub.py:1030-1045`.

**Назначение:** дать персонажу актуальное фоновое знание, *может ли игрок сейчас посетить мир, слышна ли речь, есть ли доступное обновление и откуда пришло текущее сообщение*, чтобы модель не выдавала устаревшие советы. Это user-facing интеллектуальное поведение: персонаж может обсуждать возможности своего приложения уместно, но не должен постоянно повторять диагностику.

**Runtime snapshot:**

| Поле/источник | Функциональная семантика |
|---|---|
| `PlayerMessageSource` | `APPLICATION`, `GAME`, `NONE`; принимаются legacy aliases `python`, `app`, `unity` и т. д. |
| `runtime_capabilities().connected` | Наличие активной связи с игрой; `True`, `False`, `None` имеют различную информационную определённость |
| Unity installation check | Расположение установки из настроек и действительный executable, не просто checkbox |
| `USE_VOICEOVER`, `VOICEOVER_METHOD`, `NM_CURRENT_VOICEOVER` | Выбор метода и модели речи, а не подтверждение готовности |
| `InstallableCatalogService.is_ready` | Готовность устанавливаемого локального TTS-компонента |
| `LocalVoiceService.check_initialized`, `RuntimeFeatureService.is_ready("audio")` | Фактическая инициализация модели и аудиопайплайна |
| `TelegramService.is_silero_connected` | Готовность Telegram voice-ветки |
| `RemoteVoiceService.status(character_id)` | Конфигурация и последняя проверка удалённой речи для текущего персонажа |
| `publish_python_update(available, version)` | Последнее известное уведомление об обновлении приложения |

**Выход:** текстовый `[Character Environment]` добавляется как `system` message непосредственно при сборке промпта. В нём есть ограничения наименование игрового мира NeuroMita вместо MiSide, текущая возможность доступа только к дому, источник реплики, различие между установленным/запущенным Unity и состояние голоса. Формулировки подавляют навязчивые предложения обновиться, переустановить голос или заново запустить уже открытый мир. Имеется краткое знание о различиях голосовых моделей, *это текст prompt-policy*, а не runtime benchmark качества моделей.

**Путь:** настройки и зарегистрированные сервисы → `CharacterEnvironmentContextService.snapshot()` → `format_character_environment_context(...)` → `PromptController.build()` → LLM. На GUI стороне известие о Python update публикует `presentation_hub` → тот же сервис. API-голос зависит от `current_id()` реестра, локальный голос — от selected model и каталога.

**Сценарии:**

- Игрок пишет в desktop при закрытой игре: в prompt объясняется, доступна ли установленная игра и где её запускать.
- Игрок пишет из Unity: в prompt запрещается предлагать ему «зайти в игру».
- Событие не имеет достоверного Player-transport: модель не должна предполагать источник реплики.
- Voice включён, но TTS не установлен/не инициализирован: модель знает разницу между намерением пользователя и фактической доступностью речи.
- Изменился статус приложения: context формируется заново для последующих запросов, без записи в память персонажа.

## CAP-ENV-002 — переход источника ввода игрока

**Источники:** `src/controllers/prompt_controller.py:286-312`; `src/controllers/chat_controller.py:505-520`; `src/services/contracts.py:577-600`.

Если предыдущая и текущая **достоверные** точки ввода различаются (`APPLICATION` ↔ `GAME`), в запрос добавляется отдельное `[Player Message Source Changed]` с прежним и текущим местом ввода. Если источник не указан, переход не придумывается. Это позволяет персонажу удерживать связность диалога при переключении между UI и Unity без смены собственной идентичности/истории.

## Функциональные границы и проверки полноты

- Лор мира, game state, возможность действия, диалоговое сообщение и системная осведомлённость — пять разных видов информации. Доступность функции не должна определяться только её названием в prompt.
- Static lore и runtime availability следует в спецификации паритета держать отдельно; окончательного решения о Rust сервисах здесь нет.
- Проверить на будущих parity fixtures комбинации `(world_id, character_id)`, алиасы мира, unknown world, индивидуальный override, desktop/game/unknown source, смену источника, матрицу local/API/Telegram voice и Unity not installed/installed/connected.
- Подробный Unity room/position и физическая принадлежность дома относятся к клиенту Unity; здесь изучен только контракт Core → prompt.
- **Краткая заметка об ограничении:** отдельные описания качества TTS субъективны и задаются текстом приложения; их нельзя интерпретировать как независимое подтверждённое сравнение моделей.
