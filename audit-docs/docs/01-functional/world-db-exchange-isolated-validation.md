# World DB: проверка обмена на изолированных данных (Pass 13)

Дата: 2026-10-31. Дополняет [пользовательский маршрут](world-db-json-export-import-user-workflow.md) и [обслуживание данных](data-maintenance.md). Это контракт существующего обмена, не выбор формата новой системы.

## Источник и пределы

`src/managers/database_manager.py`: `_export_excluded_columns`, `_build_status_where`, `_build_date_where`, `_build_column_filters_where`, `export_to_json_file` (1515–1740), `import_from_json_file` (1742–1858). Проверены неизменённые тела восьми методов, извлечённые AST без импорта приложения. Подменены только открытие временной SQLite-БД и получение списка колонок. Не выполнялись конструктор DatabaseManager, миграции, GUI, фоновые задачи и работа с пользовательским World.db.

Тестовая схема намеренно минимальна: history и memories с авто-ID, variables с UNIQUE(character_id,key); не объявлены дополнительные natural-key UNIQUE для history. Поэтому результат повторного импорта относится к этой схеме, а не доказывает отсутствие всех ограничений в каждой реальной версии базы.

## Подтверждённое поведение

| Сценарий | Результат source + изолированного запуска |
|---|---|
| Export для персонажа A при наличии строк B | В history, memories и variables попадают только строки A |
| Active / forgotten / deleted | У history active/forgotten определяются is_active при is_deleted=0, у памяти — is_forgotten при is_deleted=0; deleted выбирается отдельно. Комбинации объединяются OR; отсутствие выбранных применимых статусов даёт 1=0 |
| Дата range | History фильтруется по timestamp, memories по date_created; границы включены. В fixture остаётся forgotten history от выбранной даты; variables не получает этот фильтр |
| Embeddings | Все колонки с подстрокой embedding исключаются из columns и rows; импорт также их отбрасывает. Это не резервная копия embeddings/index/graph |
| Import с override C | Все три таблицы получают C; экспортированные id не переносятся, новые назначаются SQLite. eternal_id памяти в fixture сохраняется |
| Повторный import | В fixture history и memories добавляют вторые строки; variables остаётся одной строкой через INSERT OR REPLACE. INSERT OR IGNORE для history устраняет только реальные нарушения ограничений, а не произвольные семантические дубликаты |
| Ошибка записи memories после history | NOT NULL ошибка вызывает rollback всей import transaction; ранее вставленная в этом импорте history отсутствует после ошибки |

Итог повторного запуска: **PASS**, exit code 0, временные соединения закрыты и временная папка удалена. Первый запуск прошёл assertions, но завершился ошибкой уборки тестового каталога: sqlite context manager не закрывал созданные самим fixture соединения. Fixture исправлен; его оставшийся временный каталог удалён. Это ошибка тестовой обвязки, не результат исполнения приложения.

## Границы, необходимые для совместимости

- Export пишет `format=world-db-export`, `version=1`, UTC created_at, scope, options и tables с columns/rows. Import проверяет наличие tables и его тип, **не проверяет format/version**. Нельзя считать такой input автоматически строго провалидированным versioned protocol.
- History import использует INSERT OR IGNORE, memories — INSERT, variables — INSERT OR REPLACE; разрешённые колонки пересекаются с текущей схемой. Неизвестные колонки пропускаются. Строки, не являющиеся dict, пропускаются. Это не полное восстановление исходной SQLite-БД.
- Экспорт потоковый (fetchmany 500), импорт загружает JSON целиком и формирует values каждой таблицы в памяти. Симметричной гарантии по памяти нет.
- Export пишет непосредственно в выбранный файл; атомарная замена через временный файл здесь не предусмотрена. Наличие файла после исключения не доказывает завершённый экспорт.
- Import progress callback вызывается один раз до записей с (0,1); циклического checkpoint отмены внутри executemany здесь нет. Внешняя оболочка задачи не превращает этот метод в прерываемый import посреди таблицы.
- Колонки фильтров, scalar/list/LIKE и missing-column fallback исследованы по исходнику, но отдельные случаи каждого фильтра не исполнялись. Контроль реальных legacy exports, attachments, derived indexes и UI error/cancel остаётся отдельной интеграционной проверкой.

## Требования к проверке будущего паритета

`REQ-DATA-EXCHANGE-001`: обмен должен явно различать перенос history/memories/variables и полный backup; описать scope персонажа, преобразование ID и судьбу производных индексов.

`REQ-DATA-EXCHANGE-002`: контракт повторного импорта, ошибки и атомарности должен быть явным. Fixture: A/B → export A → import C → repeat → constraint failure; проверить данные всех таблиц после каждого шага. Исправление семантики дедупликации допустимо отдельным решением, копировать INSERT-политику Python как обязательную архитектуру не требуется.
