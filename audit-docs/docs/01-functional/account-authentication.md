# Browser sign-in, аккаунты и защищённые OAuth credentials

**Capability:** CAP-AUTH-PLAN-001. **Статус:** EXPERIMENTAL/CONDITIONAL, так помечен и самим UI descriptor. Подтверждена реализация в коде; работоспособность remote flow и доступность его для конкретного аккаунта не проверялись.

API profile chatgpt_plan_default вместо обычного ключа предоставляет sign-in, добавление аккаунта, выбор сохранённого аккаунта, выход, обновление model list и usage-state. UI прячет endpoint/key/reserve-key controls для этого descriptor, показывает сообщение про experimental plan quota; они не определяют сами по себе фактический remote entitlement.

ChatGPTPlanAuth открывает системный browser через stdlib webbrowser. В процессе приложения временно поднимается HTTP callback server на127.0.0.1:dynamic_port/auth/callback. Код генерирует PKCE S256, state, nonce, host registration identity; ждёт callback до1800 s, затем закрывает server, проверяет state/error/client registration, меняет code на token. Это browser OAuth/loopback function, а не автоматизация DOM через nodriver. User cancellation token в event.wait не передаётся.

ID token проверяется RS256 по загруженному OIDC discovery/JWKS, далее issuer/audience/nonce/expiration/subject. Crypto.Hash/SHA256/RSA/pkcs1_15 — использование pycryptodome именно в core auth. Refresh обновляет credentials/scopes, terminal refresh errors очищают token fields и требуют повторного входа. Запись после browser flow fenced по auth_revision/host/account identity, чтобы поздний callback не заменил уже изменённую регистрацию.

Storage Windows-only: constructor отклоняет non-Windows; account records зашифрованы Windows DPAPI через win32crypt, внешний JSON содержит envelope/active registration/host/revision. Старые unprotected account records отклоняются; запись tmp+replace. portalocker защищает сессию между процессами, RLock внутри процесса; чтение/refresh/write в session. Это разные требования: secret encryption, OS credential identity, serialization и multi-process refresh locking. В новом core можно реализовать их средствами ОС и другой crypto/OAuth stack.

Пользователь может переключить сохранённый account, добавить новый, выйти. Sign-out пробует remote revocation, затем локально удаляет tokens активной регистрации и сохраняет другие registrations; результат revoked=False явно сообщается как локальный выход без подтверждённого remote revoke. Выбор аккаунта при необходимости refresh-ит tokens, при ошибке может восстановить прежний активный account. Account labels содержат email/client registration id.

Provider извлекает access token+account identity, принимает только exact destination https://api.openai.com/v1/responses, запрещает auth/cookie/host overrides, отключает redirects и использует Responses/SSE policy. Usage/eligibility/auth/temporary errors размечаются отдельно, quota exhaustion не считается обычной transient retry; после начала body stream retry ограничен. Состояния account usage записываются в memory для GUI. Это проектная реализация experimental adapter; её endpoint/scope details не являются утверждённым публичным API contract будущей архитектуры.

Требования новой системы: при сохранении этой функции — системный browser/loopback PKCE, проверяемые token claims/signature, account-scoped immutable request credential selection, refresh synchronization, OS protected storage, различимые sign-in/permission/quota/network/remote revoke outcomes. Не требуется сохранять DPAPI envelope формат или Python классы. Наличие pycryptodome/portalocker/pywin32 не устанавливает их незаменимость в Rust; проверка альтернатив и platforms отдельно.

Источники: ChatGPTPlanAuth по всем login/refresh/token/storage/account methods; ChatGPTPlanProvider transport/error branches; provider_settings descriptor/actions; API controller и TestMixin account UI. Реальных browser launches, callback listeners, token reads, sign-in/refresh/revocation/model/API requests не было. Никакие account файлы пользователя не открывались.
