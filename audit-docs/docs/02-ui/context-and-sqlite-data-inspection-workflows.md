> Срез: локальный Python `src` из CodeNow.zip, ветвь/commit необходимо сверить с реестром ревизий. `CONFIRMED` означает подтверждённый исходниками путь, а не проведение end-to-end UI-теста. Этот документ — спецификация пользовательской функции, не проектирование будущей Rust-архитектуры.

## CAP-UI-CONTEXT — просмотр фактического запроса и ответа модели

**Статус:** `ACTIVE` (диалог вызывается действующим обработчиком действий сообщения); наполнение зависит от наличия записанного сэмпла. **Источники:** `src/ui/windows/app_window_base.py:332-387`, `src/ui/dialogs/context_viewer_dialog.py:193-269,273-378,527-620,766-812,910-1046,1538-1599`.

**Пользовательская функция.** Из действия над сообщением открывается модальный `ContextViewerDialog`, которому передаётся сохранённый сэмпл запроса/ответа. Приложение может показать конкретный запрос сообщения или последний доступный, если точный сэмпл отсутствует: при fallback пользователь получает уведомление о возможном несоответствии (`app_window_base.py:365-380`). Если нет данных, показывается предупреждение вместо пустого окна (`:344-361`).

**Контракт входных данных.** Снимок — словарь, прежде всего `messages`; возможны `model`, `provider_name`, `provider_display_name`, `protocol_id`, `dialect_id`, `timestamp`, `character_name`, `extra`, `response`, `response_raw`, `usage`, `message_meta`, `token_usage`. Данные `message_meta` используются как параллельная, не передаваемая провайдеру метаинформация об акторе (`context_viewer_dialog.py:193-240`). Содержимое может быть мультимодальным; отображение не равнозначно сериализации пользовательского запроса обратно в API.

**Операции и видимое состояние.** Вкладка «Запрос» показывает дерево «Параметры → Сообщения → логические группы → элементы» и панель просмотра; вкладка «Ответ» — `response`/`response_raw`, модель, провайдер, причину завершения и usage (`:273-378,910-1046`). Крупные группы — промпт, история, активный контекст, ввод; их порядок в дереве определяется первым появлением, а номер сообщения сохраняет исходное положение в отправленном массиве (`:527-620`). Есть поиск по содержимому, переход к следующему/предыдущему совпадению, подсветка, навигация из обзорного блока к сообщению, `Ctrl+F`, переключение pretty JSON, разворачивание окна и копирование: всего снимка, только списка `messages`, отдельного ответа/usage, параметров, группы либо сообщения (`:434-518,639-653,1538-1599`).

**Токены и стоимость.** Оценка объёма на сообщение, группу и весь запрос вычисляется локально при отсутствии `token_usage`; фактическое число входных/выходных токенов и стоимость берутся из `usage`, если присутствуют. Это **две различные семантики**: локальная оценка распределения контекста не равна счёту провайдера (`:220-239,766-812,986-1046`).

**Жизненный цикл.** Пользователь запрашивает диагностический снимок → слой действий сообщения выбирает сэмпл → UI уведомляет о fallback/отсутствии → создаёт modal viewer → viewer строит локальную навигацию и копирует данные → закрытие без модификации исходного диалога. Снимок предназначен для диагностики и анализа контекста; не добавлять требование редактирования сообщений через это окно.

**Пограничные случаи.** Отсутствие сэмпла, вытеснение данных лимитом, отсутствие ответа/usage, JSON-ответ без валидного JSON, повторяющиеся группы в непоследовательном порядке, блоки изображений, оценочные токены без точного usage. Проверять различие между запросом конкретного сообщения и последним запросом.

## CAP-UI-DATABASE — просмотр и ручное обслуживание хранилища

**Статус:** `ACTIVE`, две точки входа: с выбранным `character_id` и глобальная. **Источники:** `src/controllers/gui/character_settings_logic.py:1512-1523`, `src/ui/dialogs/db_viewer.py:85-162,163-379,450-472,570-718,727-829,903-1094,1101-1466,1470-1660`.

**Пользовательская функция.** В диалоге `DbViewerDialog` доступны таблицы `history`, `memories`, `variables`, отдельная вкладка мультимодальных изображений, опционально `embeddings`, `graph_entities`, `graph_relations`, визуальный граф. Не существующие таблицы графа и embeddings не показываются (`db_viewer.py:1512-1541`). Открытие в контексте персонажа берёт явно переданный ID либо выбранного в настройках; глобальная точка входа передаёт `None` (`character_settings_logic.py:1512-1523`).

**Сценарии чтения.** Для каждой стандартной таблицы: сортировка колонок, поиск с debounce 250 мс (все доступные текстовые колонки или выбранная), независимый фильтр по колонке/оператору/значению, фильтрация по `character_id`, скрытие удалённых записей там, где поддерживается `is_deleted`, временное отображение скрытых колонок, перенос текста и автоматическая высота строк, обновление (`db_viewer.py:239-379,450-472,570-718`). BLOB/embedding поля отображаются специальным представлением; не нужно выводить бинарные массивы как многокилобайтный текст (`:85-162`). По ПКМ доступны контекстные операции фильтрации, копирования, поиска и редактирования (`:727-829`).

**Сценарии записи.** Двойной клик по редактируемой ячейке открывает многострочный редактор с копированием и сохранением конкретного поля по `id` (`:903-989`). Выделение нескольких строк позволяет пакетно присвоить значение одной колонке; отдельное подтверждаемое действие удаляет выбранные строки (`:991-1094`). Эти действия — реальная пользовательская возможность работы непосредственно с сохранёнными данными, а не диагностическое read-only окно. Для будущего functional parity важны намерения `Inspect/Filter/Sort/EditField/BatchEdit/DeleteRows/Refresh`, а не текущая QtSql-модель.

**Изображения и метаданные.** Особая вкладка извлекает мультимодальные сообщения истории с `multimodal_parts`/`is_multimodal_list`, показывает строки с описаниями и без них, текст/путь/thumbnail; отдельный поиск; ручное редактирование описания записывается в `history.meta_data.image_descriptions.manual`. При выборе текущего описания приоритет: manual → detailed → normal → brief → первое доступное → legacy string (`:1101-1127,1206-1250,1311-1388`). Это не то же самое, что галерея снимков Unity.

**Состояние и владение.** Окно открывает собственное именованное соединение к `Histories/world.db`, настраивает SQLite busy timeout, освобождает страницы и соединение при закрытии (`:1493-1495,1616-1660`). В UI сохраняются текущие фильтры, поисковые запросы, сортировка, состояние колонок и выбранные строки, но не обязательно персистентно. Изменения затрагивают общую БД; текущий код не даёт оснований утверждать транзакционный эффект сразу для всех других доменов.

**Ограничения/вопросы:** (1) не все таблицы имеют одинаковую схему и обязательный `id`; (2) глобальный просмотр и просмотр конкретного персонажа — разные намерения; (3) одновременные обновления БД и окно просмотра требуют проверки в поведении; (4) эквивалентность GUI надо подтверждать системным тестом, сейчас подтверждён статический путь. Не смешивать эту функцию с публичным API управления памятью и историей: это интерфейс обслуживания/инспекции.

## Уточнение исходных пользовательских действий (следующий проход)

- Контекстный viewer группирует строки по логической секции, **но выводит исходный индекс сообщения**; `message_meta` — диагностические сведения об акторе вне wire payload (`src/ui/dialogs/context_viewer_dialog.py:527-618`). Ссылки `msg:<index>` открывают нужную строку, а ПКМ предлагает копирование content либо JSON конкретного сообщения (`:639-652,1538-1578`).
- **SQLite editor физически удаляет строки**: после Yes подтверждения исполняет `DELETE FROM <table> WHERE id IN (...)` (`src/ui/dialogs/db_viewer.py:991-1034`). Это отдельная power-user операция, её нельзя считать равной soft-delete и обычному CRUD памяти/истории. При double click на редактируемой ячейке выполняется конкретный SQL UPDATE по `id` (`:903-989`), BLOB/embedding защищены от обычного текстового редактирования (`:121-160`).
- Базовый chat-panel keyboard: Enter отправка, Shift+Enter ввод строки, а paste изображений перехватывает Ctrl/Meta+V и Shift+Insert; отдельный каталог доступности клавиатурных действий — [keyboard actions](keyboard-clipboard-and-direct-manipulation-contracts.md).

## Pass 13: динамическое меню SQLite и реальные границы записи

Дочитаны `DbTablePage._on_context_menu` (727–826), `_open_cell_dialog`/do_save (903–989), `_delete_selected_rows` (991–1034), `_batch_edit` (1035–1094), `_PrettySqlTableModel.flags`; сверена схема variables в `database_manager.py:681–689`. Это source review, без открытия/изменения пользовательской БД и без запуска Qt.

| Menu/action | Intent → эффект |
|---|---|
| Equals / contains текущей ячейки | Заменить пользовательский filter либо добавить AND; это не изменение содержимого записи |
| Is empty / has value | Тот же replace/AND выбор; отдельная логика пустоты вместо обычной подстановки значения |
| Search this column / all columns | Перенести cell value в search controls и применить search; поиск и user filter — разные части state |
| Hide / show all / reset columns | Меняет представление текущей вкладки; Show all временный, Reset применяет default visibility |
| Copy cell | Clipboard representation, без SQL write |
| Open cell → Save | Если editable, SQL UPDATE конкретной колонки по id с bind values; query failure остаётся в диалоге с ошибкой; success refresh и accept |
| Batch edit | Новый текст → выбранные row IDs → один SQL UPDATE колонки по id IN; отмена input ничего не записывает |
| Delete selected | Yes/No (default No) → выбранные row IDs → физический SQL DELETE; failure показывает ошибку, success refresh |
| Clear filter / clear search | Сбрасывает соответствующий пользовательский слой; clear filter сохраняет base scope |

**Нельзя обобщать доступность записи на все таблицы.** Эти три direct write пути требуют колонки `id`. Текущая таблица variables имеет composite primary key `(character_id,key)` без id. Поэтому показанные Save/Batch/Delete для неё заканчиваются отсутствием row IDs и сообщением об ошибке; наличие редактируемого widget/menu не доказывает успешный CRUD variables. Blob-like columns определяются прежде всего по подстроке embedding и лишаются editable flag; многострочное открытие embedding также прекращается до редактора.

Для таблиц с id прямой SQL не вызывает domain History/Memory API, не публикует отсюда index rebuild/effect events и не даёт общей транзакции с derivations. Подтверждённая возможность — power-user обслуживание SQL rows; синхронизация источников/индексов требует отдельного контракта новой системы. Не требуется сохранять ограничение variables как желаемое поведение, но нельзя записывать его в отчёте как уже работающий редактор.

Уточнение REQ-UI-DB-02: проверять доступность каждой операции по реальной identity/schema таблицы, success/failure/refresh и отсутствие side effect при cancel; отдельно tables с id и composite key. Остаток live QA — Qt driver locks, scroll/selection после refresh и concurrent database writers.
