## Что проверяется при новой реализации

`REQ-SET-SEMANTICS-001`: для пользовательского параметра фиксируются функция, момент применения, scope, validation и результат; показанный default, startup fallback и действие Reset различаются явно.

`REQ-SET-SEMANTICS-002`: команды archive history, forget memories и delete graph имеют разные data outcomes. Future fixture с Low/Normal/High/Critical, protected graph rows, islands, несколькими персонажами и dated rows проверяет каждый outcome отдельно.

`REQ-SET-SEMANTICS-003`: изменение модели/нормализации/search policy имеет определённый cache/reindex effect. Существующий cached helper не является требованием сохранять stale поведение.

Повторные hardware/model/Qt E2E здесь не выполнялись. Остаток: контекст остальных непрямых consumers, live editing/cache invalidation, malformed values из сохранённых настроек и интеграция maintenance с реальными многоперсонажными данными. Нельзя закрыть эти проверки одним списком найденных литералов.

## Дополнительное уточнение: два dedup и мягкий capacity

`memory_manager.py::_find_duplicate_memory` (332–380) сравнивает Jaccard token sets среди текущего character, nondeleted/nonforgotten, без islands и summary; возвращает лучший match. Отдельный MemoryDeduplicator анализирует cosine embeddings и age-dependent threshold. **Оба читают MEMORY_DEDUP_THRESHOLD**, хотя UI descriptors предлагают 0.8 и 0.94 в разных местах. Это не два разных persisted keys и не один единый semantic dedup. Для нового контракта нужно явно определить параметры двух операций.

`_forget_over_limit_memories` (400–520) считает обычные активные строки, вычисляет запас под следующую вставку как `need = active_count - (cap - 1)`, затем сортирует кандидатов по priority Low→Normal→High, retrieval bucket (access_count=0 раньше >0), возрасту и SQL id. Access count здесь бинарный сигнал, не непрерывный score. Critical/islands не выбираются жертвами; при недостатке eligible строк cap может остаться превышенным. `total_characters` — отдельный бюджет длины текста, не количество активных фактов.

Эта функция вызывается также из load_memories; комментарий «перед вставкой» не означает единственного caller. TTL вызывается в хвосте prune, а ранние return могут завершить функцию раньше него. Нельзя обещать периодическое выполнение TTL при каждом read или жёсткий database invariant `active_count≤cap`. Это source semantics, не предписание воспроизвести такое scheduling в новой системе.
