# GUI actions: freshness, serial execution and state delivery

**Цель исследования:** восстановить, что пользователь наблюдает при повторных действиях, загрузке данных, закрытии экрана и длительных командах. Это **функциональный контракт**, а не предложение переносить `IntentViewModel`/Qt/threads в Rust.

**Классификация:** `ACTIVE/CONDITIONAL` для перечисленных ниже зарегистрированных экранов; отдельный UI E2E не проводился. **Источник:** `src/controllers/gui/intent_view_model.py:18-387` и callsites в `src/controllers/gui/*_view_model.py` (см. таблицу). **Уверенность:** `CONFIRMED` для последовательностей кода; `UNRESOLVED` для фактической доставки конкретному Qt-окну в live application.

## Пользовательские правила — три независимых вида работы

| Вид | Наблюдаемый смысл | Правило обработки | Примеры фактических потребителей |
|---|---|---|---|
| **Latest result** (`run_latest`) | Быстрое изменение выбора/фильтра не должно возвращать на экран устаревшее значение | Каждый запуск для одного имени повышает generation; старый worker может физически закончить, но его результат и ошибка не применяются, если он не последний | Выбор фото в галерее (`gallery_page_view_model.py:84`), выбранный пресет embeddings (`embed_provider_view_model.py:208`), получение настроек компонента AI Hub (`ai_hub_settings_view_model.py:224`), hardware/topology AI Engine (`ai_engine_settings_view_model.py:91-149`) |
| **Exclusive operation** (`run_exclusive`) | Повторное нажатие не запускает ту же операцию параллельно | Второй вызов с тем же ключом при `inflight` отвергается, затем операция снимает занятость; успех/ошибка попадают на UI thread | Открыть папку галереи (`gallery_page_view_model.py:77`), принять и подготовить AI Hub action (`ai_hub_view_model.py:242`), сохранить embeddings-пресет (`embed_provider_view_model.py:245`), собрать Beat cache (`beat_settings_view_model.py:130`), применить обновления (`home_page_view_model.py:664`) |
| **Coalesced refresh** (`run_coalesced`) | Поток событий обновления не обязан запускать отдельный полный запрос на каждое событие | Пока выполняется одна загрузка, повторное обращение отмечает необходимость ещё одного запуска; используется последняя переданная спецификация; промежуточный результат при pending refresh не выдаётся пользователю как окончательный | AI Hub status (`ai_hub_view_model.py:140`), галерея scan (`gallery_page_view_model.py:60`), Новости (`news_page_view_model.py:62`), Logs (`logs_page_view_model.py:36`), Sandbox selectors/status/memory/budget (`sandbox_page_view_model.py:195-265`) |

Для одного имени типы запросов не эквивалентны: заменять `latest` на `exclusive` означало бы показывать устаревшую выбранную фотографию; заменять `exclusive` на `latest` допускало бы наложение несовместимых операций; заменять `coalesced` на «просто drop» могло бы потерять последнее событие изменения данных. Это *следствия наблюдаемого поведения*, не предлагаемая структура Rust.

## Состояния и временные эффекты

1. `dispatch(intent)` выбирает обработку команды; типизированное `StateT` публикуется через `state_changed`, отдельные UI-эффекты — через `effect_emitted` (`intent_view_model.py:26-81`). Наличие события состояния не доказывает, что работа завершена.
2. Worker выполняется под `task_supervisor()` и направляет колбэк через queued signal на Qt thread (`intent_view_model.py:114-162,216-278,376-387`), затем применяется `on_success` или `on_error`. UI thread не должен блокироваться на чтении файла, скане gallery, network/status или иных фоновых задачах.
3. При `close()` отключаются подписки и отменяется управление owner; поколения делаются недействительными. Физического `join` worker на UI thread нет; завершивший позже worker **не** вправе менять закрытый экран (`intent_view_model.py:88-112`).
4. При coalesced refresh повторное событие во время `inflight` создаёт ровно *один pending rerun* в текущем цикле; он использует последнее переданное описание (`intent_view_model.py:223-229,280-304`). Число входящих событий не равно числу реальных загрузок.
5. Некоторые действия имеют **дополнительный пользовательский протокол**, а не только `exclusive`: у AI Hub prepare происходит отдельно от `ConfirmBackendInstall`/`PrepareComponentInstall`, после чего возможен submit в backend FIFO (`ai_hub_view_model.py:171-260`). Занятость UI preparation не равна наличию задачи в backend queue.

## Сценарии и пограничные ситуации

- **Быстрый просмотр файлов**: выбор фото A → B, затем A загружается позже B. Вызов `run_latest("gallery-photo")` разрешает доставить результат только поколения B, сохраняя актуальный выбор; ошибки A также не должны заменить состояние B.
- **Новые фотографии во время сканирования**: повторный `RefreshGallery` во время скана не создаёт независимый полноценный scan per event; `coalesced` переносит на следующий цикл последнюю спецификацию. При изменении каталога очищаются запрошенные thumbnails и пересчитывается `revision` (`gallery_page_view_model.py:43-72`).
- **Загрузка thumbnails**: до 12 фото за один batch; по завершении даже частично неуспешной загрузки запускается следующий проход очереди (`gallery_page_view_model.py:95-128`). Отказ одного снимка не равен отмене всей галереи.
- **Отправка изображения**: чтение пользовательских файлов и скриншот — отдельные `exclusive` операции (`chat_panel_view_model.py:287-328`), затем staging изменяет `staged_count`, обновляет `can_send` и публикует `ChatImagesStaged` вместе с `Events.Chat.STAGE_IMAGE`. Допуск к отправке зависит также от готовности backend и системных опций автоматического захвата (`chat_panel_view_model.py:148-172,294-302`).
- **Переключение страницы/закрытие**: ранее выданный worker может ещё физически выполняться, но закрытый UI не принимает его результат. Функциональный критерий — отсутствие устаревших UI effects после смены жизненного цикла экрана, а не конкретная механика Qt signal.

## Измеримый список зарегистрированных потребителей

AST-инвентаризация вызовов `run_latest`, `run_exclusive`, `run_coalesced` в `src/controllers/gui/*_view_model.py`: **52 callsites в 20 модулях**. Из них: загрузка/отбор последнего значения, эксклюзивная команда или объединение refresh. Это *синтаксическая* карта потребителей; один callsite может быть недостижим в конкретном режиме, пока не подтверждён путь экрана до вызова. Точные функции и строки можно восстановить по вызовам в соответствующих source files; полностью автоматически объявлять все 52 `ACTIVE` нельзя.

## Требования к функциональному паритету

- `REQ-GUI-ASYNC-001`: смена выбора/параметров должна исключать публикацию результата устаревшего запроса на текущем экране.
- `REQ-GUI-ASYNC-002`: повторная эксклюзивная команда для одного ресурса/операции не должна создавать дублирующиеся concurrent side effects.
- `REQ-GUI-ASYNC-003`: серия одинаковых refresh triggers должна в итоге предоставить последнее актуальное состояние, не умножая полную работу на число сигналов.
- `REQ-GUI-ASYNC-004`: закрытие/удаление экрана прекращает его подписки и публикацию результатов; длительная работа не блокирует UI.
- `REQ-GUI-ASYNC-005`: промежуточные UI states (`loading`, `preparing`, `queued`, `running`, `ready`, `error`) не должны сливаться в один булев `busy`; набор состояний зависит от функции.

**Проверки будущего паритета:** две загрузки с инверсией порядка завершения; 10 refresh events при одном долгом запросе; двойной submit; close во время worker; file/gallery batch partial failure; AI Hub preview + confirm + FIFO. Требуются тесты поведения новых компонентов и Qt/Windows E2E для проверки прежнего UI, которые здесь не запускались.
