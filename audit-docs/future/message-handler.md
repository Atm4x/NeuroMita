# MessageHandler: очередь, состояние и право выполнения

Обновлено 2026-10-31. [Общая модель](current-model.md), [ChatApi](chat-api-contract.md). Это новая модель запросов; совпадение с отдельными возможностями Python TaskManager не задаёт реализацию.

## Ответственность

MessageHandler принимает обращения в свою очередь, последовательно приобретает право их выполнения, получает субъективный контекст через CharacterHandle, вызывает генерацию, организует принятие результата и завершает запись запроса.

Он не владеет живым Character и не составляет историю самостоятельно. CharacterHandler предоставляет данные и контролирует изменения персонажа. Длительное ожидание LLM не блокирует обслуживание коротких команд владельца персонажа.

## Объекты

| Часть | Содержание |
|---|---|
| RequestRegistry | Map RequestId → RequestRecord активных обращений; состояния, отмена, наблюдение |
| MessageHandler | Ограниченная очередь, потребитель и доступ к необходимым контрактам |
| RequestRecord | Неизменяемый Message, адрес/область, отмена, публичное состояние, внутренняя фаза принятия и результат |
| RequestWork | Данные одного обращения и выданное registry право выполнения |
| RequestHandle | Доступ отправителя/наблюдателя к одному обращению |
| CharacterHandle | Типизированный доступ к владельцу конкретного персонажа |
| GenerationRequest | Зафиксированный CharacterContext и ResolvedPreset |
| Пакет принятия | Подготовленный ответ и эффекты, ещё не применённые к миру |

RequestWork не удерживает блокировку map на время await. Право исполнения ограничено конкретным обращением; запоздавший callback не может повторно завершить запись.

## Адрес и очередь

Текущая рекомендация — последовательная очередь персонажа в явно определённой области мира. Точный ключ handler ещё надо закрепить.

Для одного персонажа следующий запрос начинается после завершения принятия предыдущего результата. Разные персонажи могут генерироваться конкурентно. Ограничения общих ресурсов согласуются у их владельцев, а не одним lock вокруг всей генерации.

## Приём обращения

1. Обязательные входы и адрес представлены типами. Ресурсы, требующие разрешения, проверяются соответствующим владельцем.
2. Обращение получает RequestId и отмену до начала исполнения. Фиксируется исходная область мира.
3. Регистрация, резервирование ёмкости и публикация в очереди согласованы. Потребитель не видит UID без записи.
4. Принятый запрос получает Pending; отправителю возвращается RequestHandle.
5. Registry сообщает о принятом обращении механизму обнаружения запросов.

При заполненной/закрытой очереди возвращается явный отказ. Предложен nonblocking admission: без скрытого ожидания свободного места. Если внутренний ID создан до отказа, точная форма диагностического отказа ещё не выбрана; клиент не получает ложного подтверждения приёма.

## Публичная state machine

Предложенная форма закрепляет согласованное разделение исполнения и исхода:

```rust
pub enum RequestState {
    Pending,
    Processing(ProcessingStage),
    Finished(RequestOutcome),
    Cancelled(CancellationOutcome),
}

pub enum ProcessingStage {
    GeneratingText,
    GeneratingVoice(TextResult),
}

pub enum RequestOutcome {
    Success(ResponseResult),
    TextGenerationFailed(TextGenerationError),
    VoiceGenerationFailed {
        text: TextResult,
        error: VoiceGenerationError,
    },
    InternalError(InternalFailure),
}
```

Типы полезной нагрузки пока не реализованы. ResponseResult должен различать запрошенные результаты; отсутствие необязательной озвучки не является ошибкой. InternalFailure сохраняет доступные частичные результаты без ложного утверждения, что они приняты.

Переходы Pending → Processing → Finished либо отмена имеют одного владельца. Terminal состояние не возвращается в Processing. Retry исполнения является новым обращением со связью с предыдущим, если такой сценарий предусмотрен.

При переходе к озвучке текст уже подготовлен, но ещё не обязательно принят как ответ персонажа. Если он доступен наблюдателю, степень готовности должна быть явной.

## Отмена

Pending можно отменить до чтения контекста и внешней работы. Атомарный try_start конкурирует с такой отменой. Отменённый UID можно оставить в физической очереди и пропустить при чтении; немедленное освобождение её ёмкости требует отдельного механизма.

При Processing отмена запрашивает остановку оставшейся работы. Публичный Cancelled фиксируется после подтверждённой остановки, а не только после нажатия кнопки.

Отмена до принятия результатов запрещает применение подготовленных эффектов. Во внутреннем Working право отмены ещё есть; после перехода в Accepting отмена возвращает TooLate.

Проверка отмены и переход к Accepting — одна согласованная операция. Отдельная проверка token перед независимым началом применения оставляет гонку.

## Внутренняя фаза принятия

Для всего пакета результата предложен enum EffectPhase: Working, Accepting, Applied, Discarded. Публичное состояние во время Working/Accepting может оставаться Processing.

Это часть записи выполнения, а не произвольный флаг внутри handler. Проверка отмены не требует заглядывать в код генератора. Внешний статус и фаза изменяются согласованно одним владельцем.

Finished публикуется после принятия результата и обработки исхода. Поведение при частичном сбое Accepting ещё надо определить; enum сам по себе не реализует транзакцию и восстановление.

## Область мира и контекст

При постановке фиксируется admission_scope: принадлежность исходному миру и необходимые версии. При обработке получается фактический context_anchor. Это разные привязки.

Причина запроса не заменяется tail истории после ожидания. Обычное развитие текущей ветки допустимо; переключение мира и сброс контекста требуют обнаружения устаревшей работы. Подробности: [SessionTimeline](session-timeline.md).
