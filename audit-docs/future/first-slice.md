# Первый исполняемый срез

Историческая запись. Актуальная реализация расширена до [минимальных контрактов](minimal-contracts.md); ограничения ниже относятся к первому срезу.

Реализован 2026-10-31 в [audit-docs/rust](../rust/README.md). [Навигация](README.md). Это начальная реализация части согласованной модели, а не полный перенос Python-функционала.

## Реализованный путь

Консольная привязка вызывает ChatPresenter. Presenter создаёт валидированный UserInput и ReplyRequest с явно заданным GenerationPreset, затем вызывает статический ChatApi::reply.

ChatApi резервирует место в ограниченной очереди, регистрирует обращение и возвращает RequestHandle. Нет ожидания LLM под общим admission lock. Исходный Message хранится до старта/отмены и освобождается после передачи в работу.

MessageHandler последовательно обслуживает очередь персонажа. Получает контекст у CharacterHandler, выполняет генерацию через ResponseGenerator, атомарно получает право Accepting и принимает ответ с эффектом. Только после этого публикуется Finished и начинается следующий запрос.

Registry предоставляет обнаружение принятых запросов и наблюдение конкретного состояния. ChatPresenter самостоятельно обнаруживает также прямые внешние вызовы ChatApi, поэтому будущий сервер не должен уведомлять GUI вручную.

## Типизированный пресет и провайдерский контракт

Уточнение пользователя: проектировать общий путь универсально, Gemini — только один провайдер. Пресет содержит именно типизированный шаблон провайдера.

Реализованы GenerationPreset → ProviderTemplate::Gemini(GeminiTemplate), GenerationProvider и явная таблица зарегистрированных провайдеров. Это маршрутизация исполнителя по типу, не поиск/выбор пресета.

URL, авторизация, systemInstruction, contents, generationConfig и decode находятся внутри generation/gemini. Общее приложение и presenter передают GenerationRequest с CharacterContext и GenerationPreset. Нет общего HTTP-предположения в контракте GenerationProvider.

Новый провайдер добавляет свой вариант типизированного шаблона и реализацию порта. Предварительно не создаются фиктивные OpenAI/Anthropic реализации.

В первом срезе пресет передаётся значением, а не через PresetRef/revision и каталог. Это намеренное упрощение по запросу пользователя: нет ротаций, поиска и CRUD. Настройки шаблона валидируются при создании; пропущенные модель/ключ и неверные значения дают ошибку.

## Состояния и отмена

В срезе есть Pending, Processing(GeneratingText), Finished(Success/TextGenerationFailed/InternalError), Cancelled. Озвучка отсутствует, поэтому её состояния не объявляются реализованной возможностью.

Внутренняя фаза: Working/Accepting/Applied/Discarded. Отмена и начало принятия защищены одной короткой операцией записи. До Accepting отменяется ожидаемая работа/HTTP future. Во время Accepting возвращается TooLate.

Каждая работа исполняется в контролируемой дочерней задаче; её неожиданный выход завершает запрос InternalError. Очередь ожидает завершения этой задачи и продолжает обработку следующей работы.

Registry удаляет terminal запись. Существующий handle содержит terminal снимок. Начальное состояние и subsequent watch обновления доступны без polling. Снимок содержит монотонную revision.

## Контекст и история

Стартовые персонажи: Mita и KindMita с минимальными новыми описаниями/промптами. Это не полный набор Python-персонажей и не сохранение их поведения.

На начале обработки владелец получает историю своих наблюдений, записывает входной факт и фиксирует anchor. Текущий вход не дублируется в исторической части Gemini-запроса. Следующая работа того же персонажа получает уже принятый предыдущий ответ.

История общая по хранению, субъективная по выборке. Контекст одного персонажа не включает приватные обращения другого. В этой версии нет смены ветки, reset знаний, checkpoints и чтения произвольного исторического состояния.

Генератор Gemini возвращает только видимый текст. Thought parts не выдаются за ответ; blocked/пустой/незавершённый ответ считается ошибкой, а не успехом.

## Принятие в памяти

Подготовленный текст принимается через владельца персонажа. Перед изменением проверяются версия state и допустимость связи с timeline. Все fallible проверки выполняются до изменения данных.

В коротком синхронном участке владельца под общей защитой timeline записывается ответ и обновляется state. Эффект RecordAcceptedReply увеличивает счётчик принятых ответов и revision. Ошибка генерации/отмена не увеличивают счётчик и не создают ответ.

Это согласованная операция в памяти для текущего ограниченного эффекта, не универсальная транзакция БД. Durable commit, произвольные эффекты и восстановление после crash остаются отдельной работой.

## Presenter и frontend

GuiPresenter содержит ChatPresenter. Его команды вызывают ChatApi, а его модель обновляется независимо от frontend.

Консольная привязка отправляет действия через presenter и наблюдает его модель. Она не читает напрямую Character/SessionTimeline и не формирует провайдерские сообщения.

Presenter наблюдает новые обращения через broadcast и каждый запрос через watch. Активные обращения не обрезаются; число сохраняемых завершённых строк ограничено параметром. Отставание discovery явно отражается в модели, затем восстанавливается список активных запросов. История всех пропущенных завершённых запросов не восстанавливается автоматически.

Slint, TUI-рендерер, SettingsApi и bindable настройки пока не реализованы. Контракт presenter остаётся пригодным для их подключения без переноса генерационной логики в UI.

## Проверки и фактические границы

[Интеграционный сценарий](../rust/tests/vertical_slice.rs) проходит через реальный HTTP-адаптер к локальному серверу формата Gemini. Проверяются заполнение очереди, отмена pending/running, независимая работа персонажей, история после принятия, отсутствие эффектов отменённой работы, ошибки HTTP, изоляция паники обработчика и shutdown.

Unit-проверки покрывают гонку отмены/Accepting, terminal handles, строгую конфигурацию и redaction ключа, разбор Gemini, исключение reasoning и ошибки неполного ответа.

Живой Gemini не вызывался: в окружении сессии нет API-ключа. Модель пользователь задаёт явно. Реализация готова к запуску с его локальным окружением; сведения о фактическом качестве/доступности выбранной модели этим тестом не подтверждаются.

Остальные архитектурные документы описывают целевую модель; этот файл фиксирует реализованное подмножество.
