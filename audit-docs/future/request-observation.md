# Наблюдение за запросами, обнаружение и техническая история

Обновлено 2026-10-31. [Навигация](README.md).

## Два разных наблюдения

1. Обнаружить запрос, принятый из любого источника.
2. Наблюдать состояние конкретного запроса.

GUI должен видеть также обращения, отправленные ServerLifecycle. Для этого registry предоставляет общий механизм обнаружения. Сервер не вызывает GUI и не знает его виджеты.

## Наблюдение одного запроса

RequestHandle предоставляет идентичность, актуальный снимок, ожидание изменений, отмену и итог. Точная форма методов ещё уточняется; обсуждены id(), snapshot(), observe(), cancel().

```rust
pub struct RequestSnapshot {
    pub id: RequestId,
    pub revision: u64,
    pub state: RequestState,
}
```

Состояние содержит относящиеся к нему данные. Итог ошибки озвучки включает рабочий текст. Изменение статуса и запись соответствующих данных не публикуются независимо.

Согласовано: ожидание асинхронное, не блокирует GUI и не использует периодический polling. Публикация состояния пробуждает ожидающую задачу.

Предложена семантика наблюдения за последним состоянием: медленный потребитель может пропустить промежуточные снимки, но получает актуальный и окончательный результат. Это не журнал обязательной доставки каждого перехода. Если потребуется такой журнал, контракт нужно расширить.

Первое получение даёт актуальный снимок, в том числе уже завершённого запроса. Подключение согласовано с чтением состояния. Отключение наблюдателя само по себе не отменяет работу.

## Механизм-кандидат

Показан tokio::sync::watch:

- при регистрации создаётся канал с исходным снимком;
- отправляющая сторона находится у владельца записи;
- handle предоставляет получателя;
- changed().await ожидает изменения;
- borrow_and_update() читает снимок и отмечает его полученным;
- снимок клонируется/разделяется по владению без удержания borrow через await;
- send_replace сохраняет последнее значение даже при отсутствии получателей.

В [первом срезе](first-slice.md) выбран Tokio: watch для состояния конкретного запроса и broadcast для обнаружения принятых обращений. Ниже описан его контракт; остальные runtime-решения не следуют автоматически из этого выбора.

Если канал закрыт до terminal состояния, это отдельная ошибка наблюдения/исполнения. Закрытие нельзя выдавать за Success.

Обсуждённый пример потребителя; RequestSnapshot и проверка terminal состояния относятся к доменному контракту:

```rust
use std::sync::Arc;
use tokio::sync::watch;

pub enum ObserveError {
    ClosedBeforeCompletion,
}

pub async fn observe_request(
    mut updates: watch::Receiver<Arc<RequestSnapshot>>,
    mut on_change: impl FnMut(Arc<RequestSnapshot>),
) -> Result<(), ObserveError> {
    loop {
        let snapshot = {
            Arc::clone(&*updates.borrow_and_update())
        };

        let finished = snapshot.state.is_terminal();
        on_change(snapshot);

        if finished {
            return Ok(());
        }

        updates
            .changed()
            .await
            .map_err(|_| ObserveError::ClosedBeforeCompletion)?;
    }
}
```

Это документационный фрагмент, не добавленный модуль проекта. GUI callback ставит обновление в очередь GUI-потока, ServerLifecycle — в очередь отправки. Длительная отправка не выполняется синхронно в on_change. Lifecycle запускает и завершает наблюдающие задачи.

## Обнаружение обращений

Обсуждённый вход ChatApi::observe_requests() должен предоставлять согласованный начальный список активных работ и уведомления о новых принятых запросах.

```rust
pub struct RequestAccepted {
    pub request: RequestHandle,
    pub character_id: CharacterId,
    pub origin: RequestOrigin,
}
```

Состав RequestOrigin ещё не утверждён. Он описывает происхождение, не зашивает Unity в ядро. Уведомление публикуется для принятого обращения после согласованной регистрации.

Handle в уведомлении сохраняет доступ к результату, даже если работа завершилась до подключения наблюдения одного запроса. Запрос, отправленный самим GUI, сопоставляется по RequestId и не добавляется в UI второй раз.

Один watch последнего созданного запроса здесь не подходит: быстрые регистрации вытеснят друг друга. Нужен поток отдельных уведомлений. Начальный список и начало потока не имеют окна потери.

Лимит буфера, обнаружение отставания, восстановление и срок удержания уведомлений пока открыты. Нельзя обещать доставку каждого принятого обращения при произвольном отставании без соответствующего хранения/подтверждения.

## Потребители

| Потребитель | Реакция |
|---|---|
| ChatPresenter / RequestsPresenter | Обнаруживает обращения, следит за ними и меняет наблюдаемую модель интерфейса |
| GUI binding | Переносит новую модель в поток GUI и устанавливает свойства компонентов |
| ServerLifecycle | Связывает RequestId с клиентским обращением и передаёт статусы/результаты по протоколу |
| TUI/CLI | Выводит состояние либо ждёт результат согласно своему сценарию |

Длительная отправка по сети и отрисовка не выполняются внутри блокировки registry. Отказ доставки не превращает уже принятый ответ персонажа в ошибку генерации.

## Время жизни записей

RequestRegistry — учёт живой работы, не обязательный вечный архив. После завершения запись может удаляться из map; существующие handles сохраняют итог, пока он им нужен. Конкретное владение и retention ещё не выбраны.

При открытии интерфейса можно получить активные обращения. Показ прошлых завершённых запросов является отдельной возможностью технической истории.

## Технический след запроса

Предложена отдельная структурированная запись RequestTrace, если требуется диагностика:

- RequestId и причина обращения;
- исходная область и фактически использованный context_anchor;
- версия пресета;
- подготовленный вход и выполненные преобразования;
- этапы, длительности, результаты и ошибки.

Хранение в БД возможно, но не утверждено. Авторизационные секреты не нужны как часть диагностической записи провайдерского запроса.

SessionTimeline хранит смысловой ответ и связь с RequestId; он не обязан владеть полным техническим описанием сборки. Сам UUID не гарантирует, что диагностика сохранена.

## Открытые решения

Гарантии обнаружения при отставании; сроки жизни terminal снимков и traces; повторное наблюдение после сетевого reconnect; сохранение после рестарта; граница между статусами и отдельным потоком текстовых/аудиочанков.

## Источники механизмов

[Tokio watch](https://docs.rs/tokio/latest/tokio/sync/watch/), [send_replace](https://docs.rs/tokio/latest/tokio/sync/watch/struct.Sender.html#method.send_replace). Это кандидаты реализации согласованного контракта.
