# Lifecycle, сборка и владение

Обновлено 2026-10-31. [Навигация](README.md).

## Lifecycle как примитив

Lifecycle — экземплярный активный исполнитель с собственными ресурсами, задачами и временем жизни. Он подготавливает ресурсы, исполняет работу, принимает остановку, завершает дочерние задачи и возвращает результат/ошибку.

Обсуждён контракт вида run(stop_token). Это одна операция, живущая всё время исполнения. Точный Rust trait, типы завершения и async runtime пока не утверждены.

Api — статические вызываемые операции. Lifecycle — экземпляры, которые исполняются. Статический Api может направлять обращение в очередь, обслуживаемую Lifecycle/handler.

## ServerLifecycle

ServerLifecycle не привязан к Unity. Он обслуживает клиентов, понимающих заданный сетевой контракт: Unity, Desktop Mate и другие.

Его ответственность:

- транспорт, соединения и сетевые задачи;
- декодирование/проверка формы команд протокола;
- вызов подходящих статических Api, например ChatApi::reply;
- связь клиентского обращения с RequestId и наблюдением;
- передача статусов, результатов и обновлений;
- согласованная остановка собственной работы.

Названия UnityChatEndpoint и UnityIntegration для этого общего исполнителя отвергнуты. Клиентские особенности описываются контрактом данных; универсальный сервер не должен определяться названием одного клиента.

Настройки соединения, общие пользовательские настройки и состояние персонажей имеют разных владельцев. ServerLifecycle маршрутизирует команды соответствующим операциям, а не записывает произвольные поля ядра.

## Иерархическая сборка

ApplicationLifecycle знает крупные части приложения и их предоставляемые возможности. Каждый модуль создаёт собственные внутренние объекты и получает внешние зависимости явно.

```text
ApplicationLifecycle
├── владельцы ядра и инициализация статических Api
├── ServerLifecycle
├── GuiPresenter
│   ├── ChatPresenter
│   ├── SettingsPresenter
│   └── другие функциональные presenters
├── GuiLifecycle
│   └── Slint-привязки к presenter
└── TerminalLifecycle
    └── терминальные привязки к presenter
```

Это схема обязанностей, не готовая структура всех runtime-типов. GuiPresenter самостоятелен относительно виджетов. GUI и TUI вызывают его контракты и наблюдают модели.

Один bootstrap, вручную создающий все детали всех подсистем, не требуется. В частности, верхний уровень не должен знать поля каждой UI-секции.

Статические Api связываются с исполнителями до начала приёма внешних команд. Во время shutdown прекращается приём и завершаются работы по ещё уточняемой политике. Доступ к остановленному исполнителю даёт явный результат, а не скрытую переинициализацию.

## Персонажи и владельцы

Состав персонажей задаётся явно в коде. Создаются Character, его CharacterHandler и CharacterHandle. Registry содержит Map CharacterId → CharacterHandle.

CharacterHandler исключительно владеет живым экземпляром Character. Внутри Character находятся неизменяемые definition/описание/промпты и изменяемый state. Изменения доступны через типизированные операции владельца. Сам Character может проверять допустимость изменений.

Предложенный механизм доставки — очередь коротких типизированных команд владельцу с ответами. Наблюдение и изменения персонажа не должны ждать долгую генерацию LLM. Точная реализация mailbox пока не выбрана.

CharacterRegistry занимается получением handle, а runtime управляет жизнью обработчиков. MessageHandler хранит адрес/handle, а не становится вторым владельцем Character.

## Владение в Rust

Arc означает совместное владение; он не делает состояние автоматически изменяемым или синхронизированным. Не требуется помещать каждый сервис в Arc.

Используются подходящие по времени жизни формы: владение ресурсом, канальный handle, заимствование, совместное владение там, где оно обосновано.

Нельзя механически сложить владельцев и ссылки на их соседние поля в самоссылочную структуру App. Ранние примеры локальной сборки со ссылками были иллюстрациями, не готовым решением для 'static GUI callbacks и фоновых задач.

Статический Api должен иметь корректный по сроку жизни внутренний доступ. Однократная установка канальных handles — возможная реализация, но конкретный глобальный контейнер/OnceLock ещё не выбран.

## Структура исходников: направление

На старте достаточно одного crate с модулями. Разделение на crates core, presentation, gui, terminal обсуждалось как возможность; оно не реализовано и не является обязательным начальным workspace.

```text
src/
├── main.rs
├── app/             # корневой lifecycle и сборка
├── api/             # статические входы
├── response/        # запросы, registry, очередь, исполнение
├── character/       # Character, владелец, registry, каталог
├── timeline/        # факты, ветки, знания, чтение
├── generation/      # пресеты, подготовка, протоколы, эффекты
├── settings/        # структуры разделов, владелец, сохранение
├── presentation/    # корневой и дочерние presenters
├── server/          # ServerLifecycle и сетевой контракт
├── gui/             # Slint и bindings
├── terminal/        # CLI/TUI
└── infrastructure/  # конкретные хранилища и провайдеры
```

Это ориентир размещения по ответственности. Файл не требуется для каждой маленькой структуры, и модули не создаются до реализации соответствующего функционала.

В [первом срезе](first-slice.md) добавлены ApplicationLifecycle, владельцы персонажей, статический ChatApi, очередь, presenter и провайдерская генерация. Используются Tokio, UUID, reqwest и serde. GUI и БД пока не подключены.

## CLI и процессы

Отдельный crate не означает отдельный серверный процесс. GUI и terminal могут использовать одно ядро как библиотеку.

Если CLI должен управлять уже работающим приложением, нужен явный IPC/сетевой контракт. Эта возможность не выводится автоматически из разделения crates и пока не спроектирована.
