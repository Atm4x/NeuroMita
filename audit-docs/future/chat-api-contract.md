# ChatApi: статический вход и приём обращения

Обновлено 2026-10-31. [Навигация](README.md), [обработка запроса](message-handler.md).

## Согласованная роль

ChatApi заменяет прежнее имя ResponseService. Суффикс Api является нормой для статических входов приложения. В Rust пишем ChatApi, а не ChatAPI.

Потребитель обращается напрямую: ChatApi::reply(request), ChatApi::react(request), ChatApi::initiate(request). Экземплярный Api с обязательной передачей presenter'у и дополнительный ChatCommands ради такой передачи не являются текущей моделью.

Одно ядро на процесс связывает эти входы со своими исполнителями при запуске. Статический вызов не означает выполнение под общим lock. Конкретный способ хранения и инициализации внутреннего доступа ещё не выбран.

## Семантические операции

| Операция | Назначение |
|---|---|
| reply | Ответить на конкретное сообщение |
| react | Отреагировать на событие/явно заданный вход |
| initiate | Начать высказывание по явному намерению |
| Наблюдение за запросами | Получить активные обращения и обнаруживать новые |
| Доступ к одному запросу | Прочитать состояние, наблюдать и запросить отмену |

reply/react/initiate принимают соответствующие типизированные данные. Полный набор полей и форма MessageInput ещё не утверждены. Если поддерживаются разные основания реакции, их следует выразить явными вариантами, а не набором необязательных полей с fallback.

Внутренняя общая операция отправки передаёт реализацию Message выбранному обработчику. Наличие отдельного публичного send сверх семантических методов ещё не обязательно.

## Обязательные входы

Обращение явно задаёт персонажа, вход и пресет. Предложенная обязательная часть Message:

```rust
pub trait Message: Send + Sync {
    fn character_id(&self) -> CharacterId;
    fn preset(&self) -> PresetRef;
    fn input(&self) -> &MessageInput;
}

pub struct PresetRef {
    pub id: PresetId,
    pub revision: PresetRevision,
}
```

Это эскиз контракта. Передача конкретной revision рекомендована; точный тип и представление ещё не реализованы.

Пропущенные обязательные поля отклоняются на границе внешнего ввода. Неизвестный персонаж/ресурс/версия дают ошибку соответствующего этапа. Нет выбора первого пресета, чтения текущего UI-переключателя вместо входа или скрытой подстановки.

Если проверка требует актуальных знаний персонажа, её выполняет его владелец при подготовке работы. Предварительная проверка Api не заменяет проверку перед принятием.

## Результат приёма

Предложен контракт Result<RequestHandle, SubmitError>.

- Ok означает: обращение зарегистрировано и принято в очередь, получена идентичность и управление им.
- Err означает: принять обращение не удалось, например адрес недоступен, очередь закрыта или заполнена.
- Успешный приём не означает успешную генерацию. Ошибки последующих этапов публикуются через состояние запроса.
- Вызов не ждёт LLM, озвучку или завершение принятия ответа.

Регистрация и публикация согласованы. Не допускаются потерянные записи в Pending или элементы очереди без записи.

## Идентичность

Рекомендован тип RequestId с UUID внутри. UID — общее название уникального идентификатора; UUID/GUID обозначают одно семейство идентификаторов. Конкретная версия UUID ещё не выбрана. RequestId не смешивается с CharacterId и EventId.

Источник обращения хранится отдельными метаданными. Сетевой клиент не должен быть зашит в тип Api как Unity: общий ServerLifecycle обслуживает совместимый контракт.

## Конкурентность

Три последовательных вызова Api быстро ставят три работы в очередь. Для одного персонажа исполнение последовательно по выбранной политике handler; для разных персонажей возможно параллельное.

Короткая синхронизация registry и публикации допустима. Блокировка не охватывает сетевые await и генерацию.

## Запуск и остановка

Api связываются с исполнителями до приёма внешних команд. До инициализации возвращается явная ошибка. Порядок прекращения приёма и остановки исполнителей задаётся Lifecycle.

Повторная инициализация в одном процессе, тестовая изоляция и точные правила shutdown ещё не реализованы. Гипотетическая необходимость нескольких независимых ядер не используется как основание усложнения модели.

## Сетевые повторы

Повторный текст с новым намерением — новый запрос, который обрабатывается на новой допустимой границе контекста.

Повтор той же транспортной команды после потери подтверждения — другой случай. Рекомендовано распознавать его по стабильной идентичности команды и возвращать прежнее подтверждение. Блокировка кнопки не покрывает потерю сетевого подтверждения.

Наличие автоматических повторов, ключ дедупликации, срок хранения подтверждений и поведение после рестарта пока не утверждены. Не нужно хранить весь RequestRecord только ради подтверждения повтора.
