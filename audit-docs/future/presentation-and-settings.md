# Настройки, presenters и binding

Обновлено 2026-10-31. [Навигация](README.md).

## Вывод из текущего кода

В releases SettingsController создаёт SettingsManager и регистрирует SettingsService. SettingsManager владеет registry и фоновым сохранением JSON. SettingsRegistry хранит значения str → Any, revision и подписчиков. GUI использует QtSettingsViewModel, а некоторые потребители обращаются напрямую к статическому SettingsManager.

ServerController выбирает поля для сетевого payload и рассылает изменения. В этот payload также включены character stats и описание передачи изображений; они не становятся пользовательскими настройками только из-за совместной отправки.

Количество настроек велико, пользователь оценивает его примерно в 500. Точный полный подсчёт в этой сессии не выполнялся. Общий registry не является единым строгим каталогом всех полей: встречаются отдельные схемы и разрозненные defaults.

Исходники: [SettingsManager](../../src/managers/settings_manager.py), [SettingsRegistry](../../src/core/settings_registry.py), [SettingsService](../../src/services/settings_service.py), [SettingsController](../../src/controllers/settings_controller.py), [GUI binding](../../src/ui/settings/settings_binding.py), [server](../../src/controllers/server_controller.py).

Эти факты объясняют функциональную потребность общего доступа. Их Python-архитектура не переносится автоматически.

## Модель настроек с нуля

Рекомендованы обычные структуры разделов. Поля имеют bool, числа, строки, доменные типы и вложенные структуры. Enum применяется для конечного выбора вариантов, а не как плоский список всех 500 настроек.

```rust
use std::time::Duration;

pub struct AppSettings {
    pub capture: CaptureSettings,
    pub speech: SpeechSettings,
}

pub struct CaptureSettings {
    pub enabled: bool,
    pub interval: Duration,
    pub jpeg_quality: u8,
    pub excluded_window_title: String,
}

pub struct SpeechSettings {
    pub enabled: bool,
    pub device_id: String,
    pub input_mode: SpeechInputMode,
}

pub enum SpeechInputMode {
    Radio,
    Continuous,
}
```

Это пример формы, не окончательная схема. Тип числа ограничивает представление, но не все бизнес-ограничения: например, качество JPEG дополнительно проверяется по допустимому диапазону.

Файлы распределяются по функциональным областям: settings/capture.rs, speech.rs, interface.rs, network.rs и т.д. Корневая структура перечисляет разделы, а не сотни полей подряд.

Отдельный тип ключа на каждую настройку, сотни методов Api и обязательная генерация большого каталога не приняты. Метаданные для динамических форм/провайдерских схем можно добавить при конкретной потребности.

Отсутствующее обязательное значение, неверный тип и недопустимое сочетание дают ошибку. Runtime fallback через get(key, default) не является контрактом новой системы. Первоначальное создание конфигурации и миграции надо определить отдельно.

## SettingsApi и владелец

Статический SettingsApi оправдан общими пользовательскими настройками, доступными GUI, terminal и сетевым операциям.

Предложенный SettingsLifecycle владеет значениями и исполнением сохранения. Он принимает проверенные изменения, публикует версии и обслуживает наблюдение. Точное разделение data owner и фонового writer ещё не реализовано.

Потребитель получает согласованный снимок нужного раздела. Возможная форма: SettingsApi::snapshot::<CaptureSettings>(). Набор поддерживаемых разделов закрепляется типами; форма generic trait пока не выбрана.

Изменения одного или нескольких связанных полей должны проверяться согласованно. Версия снимка может использоваться для выявления конкурентного изменения. Точная форма patch/replace ещё открыта.

Принятие значения, сохранение на диск и применение работающим исполнителем — разные результаты. Исполнитель отвечает за свои ресурсы и сообщает о неудаче применения. Владелец настроек не превращается в один обработчик с сотнями условий запуска всех подсистем.

Снимок и начало наблюдения согласованы, чтобы не потерять изменение между ними. Частые изменения UI могут объединяться для сохранения без задержки генерации и GUI; конкретная политика пока не задана.

## Границы данных

Настройки приложения, параметры пресета конкретного запроса, состояние персонажа и факты SessionTimeline имеют разных владельцев. SettingsApi не должен становиться универсальной записью всех данных.

Выбранный для запроса пресет передаётся явно. Изменение выбора в интерфейсе не подменяет уже подготовленную генерацию. Для обработки фиксируются необходимые значения настроек.

ServerLifecycle получает представление данных, предусмотренное протоколом, и передаёт изменения клиентам. Сетевая синхронизация сама по себе не делает всё содержимое payload пользовательскими настройками.

## Presenter как самостоятельная часть приложения

Согласовано: presenter предоставляет UI команды и наблюдаемые модели. Он не принадлежит конкретному виджету и не зависит от запуска Slint.

GuiPresenter может собирать ChatPresenter, SettingsPresenter и другие функциональные presenters. ApplicationLifecycle создаёт/связывает эту часть приложения. GuiLifecycle и TerminalLifecycle подключают соответствующие представления.

UI собирает введённые значения и вызывает типизированную операцию. Presenter организует взаимодействие с Api, наблюдение запросов и состояние модели. Живой Character и его бизнес-ограничения остаются у владельца персонажа, а выполнение генерации — у обработчика запроса.

Для GUI и TUI можно использовать один контракт поведения, если оно совпадает. Разметка, фокус, клавиатурные события и конкретная отрисовка относятся к frontend. Простому CLI presenter может не требоваться.

## Кастомная секция из 20 настроек

Секция предоставляет явную типизированную модель с нужными полями. Она может объединять поля нескольких разделов хранения; UI не обязан знать структуру SettingsApi.

Пример части модели: громкость, озвучивать в launcher, озвучивать в игре. Модель пополняется необходимыми полями; для кастомной разметки нормальны явные соответствия элементов и свойств.

SettingsPresenter получает исходные значения и наблюдает SettingsApi. GUI/TUI работает через контракт presenter. Не требуется, чтобы каждый control напрямую получал доступ к общему хранилищу.

## Binding вместо ручной синхронизации

Рекомендация после обсуждения: для параметров использовать типизированные bindable-свойства presenter.

Каждое свойство предоставляет текущее значение, операцию изменения с результатом и наблюдение изменений. Примеры: volume, enabled_in_launcher, enabled_in_game.

UI меняет значение через setter/операцию свойства. Внутри выполняется предусмотренное изменение через SettingsApi. Изменение из другого источника обновляет свойство и уведомляет UI.

Это соответствует идее двусторонней привязки. Она не открывает публичные mutable-поля общего store и не обходит проверку, сохранение и уведомления.

Отклонённое значение не становится подтверждённой настройкой. UI получает ошибку и актуальное значение. Оптимистический draft и форма с Apply/Cancel, если нужны, требуют отдельной явной модели.

Для отправки сообщения, проверки подключения, восстановления сессии и других действий остаются команды. Bindable-свойство не заменяет все операции приложения.

Обновление свойства из источника не должно повторно отправлять пользовательскую команду. Нужно различать принятую модель и пользовательское намерение.

Точные Rust-типы bindable property, результат setter, владение подпиской и реакция на конфликт revision ещё не реализованы.

## Slint/TUI binding

Предлагаемое размещение:

```text
presentation/settings/voice.rs    — контракт модели и поведения
gui/bindings/voice_settings.rs    — связь с компонентами Slint
gui/ui/voice_settings.slint       — кастомная разметка
```

Slint предоставляет свойства и callbacks. Binding связывает действия controls с операциями presenter и обновляет свойства из наблюдаемой модели.

Привязка <=> связывает свойства в Slint; она сама не соединяет произвольный Rust-presenter с SettingsApi. Для межпоточных обновлений используется GUI dispatcher, например Weak::upgrade_in_event_loop.

GuiLifecycle удерживает frontend-привязки и подписки на время жизни представления. Presenter может иметь собственное время жизни в приложении. Отключение представления не отменяет автоматически генерационные запросы.

Terminal использует тот же контракт presenter со своим вводом и отображением. Создание универсального набора виджетов поверх Slint и TUI не требуется.
